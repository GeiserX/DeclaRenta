# CLAUDE.md - DeclaRenta

## Project Overview

DeclaRenta converts foreign broker reports into Spanish tax declarations (Modelo 100, 720, 721, D-6). Browser-first, privacy-focused. All financial data stays on the user's machine.

- **Domain**: [declarenta.com](https://declarenta.com)
- **Alt URL**: [geiserx.github.io/DeclaRenta](https://geiserx.github.io/DeclaRenta/)
- **Docker**: `drumsergio/declarenta` on Docker Hub

### Supported Brokers (13)

IBKR (XML), Degiro (CSV), Flatex (CSV), eToro (XLSX), Scalable Capital (CSV), Freedom24 (JSON), Revolut (XLSX), Lightyear (CSV), Coinbase (CSV), Binance (CSV), Kraken (CSV), Trade Republic (CSV), Trading 212 (CSV)

## Critical Rules

### Commission Sign
- `Trade.commission` follows the broker cash sign: negative = fee charged, positive = rebate received (IBKR sends exchange/liquidity rebates as a positive `ibCommission`). Every parser emits a charged fee as negative. Trade Republic writes a paid fee negative, so it passes the `fee` cell on with its sign: a positive one is a rebate (#467). The engines read it through `commissionCost()` (fifo.ts) and the matching negation in fx-fifo.ts; never `.abs()` it, or a rebate becomes a fee counted twice.

### Financial Precision
- **ALWAYS** use `Decimal` from `decimal.js` for any monetary calculation
- **NEVER** use JavaScript `Number` for amounts, rates, or prices
- **ALWAYS** use ECB official rates (via `getEcbRate()`), never IBKR's `fxRateToBase`

### Privacy
- **NEVER** add network calls that transmit user financial data
- **NEVER** log financial amounts, NIF, or personal information
- The only permitted outbound request is to the ECB SDMX API for exchange rates

### Crypto Permuta Valuation (Art. 37.1.h LIRPF)
- Crypto↔crypto swaps (permutas) are valued via three mechanisms only:
  - **(A) Skip-and-warn**: trades we cannot value are skipped, the user is warned.
  - **(D) Cross-leg inference**: the EUR value is inferred from the resolvable side of the swap.
  - **(B) Manual entry**: the user types an EUR-per-unit value in the crypto-rates panel.
- We DELIBERATELY do NOT call any live external crypto price API/oracle (this would be "option C"). The set of {coins, dates, amounts} a user holds is a portfolio fingerprint that must never leave their machine.
- The ONLY permitted outbound call remains the ECB SDMX fiat-rate API.
- **Shared parsing**: `src/engine/manual-rates.ts` is the single source of truth for turning raw `{currency,date,eurPerUnit}` quotes into an `EcbRateMap` (date→YYYY-MM-DD, currency upper-cased + stablecoin-normalized, rate validated with Decimal). Both the web localStorage path and the CLI `--crypto-rates` flag consume it — never re-implement the validation inline.
- **Known limitation (cross-date phantom gain)**: dropping an unresolvable BUY leg creates no FIFO lot, so a later *resolvable* SELL of that coin taxes full proceeds as gain (costBasis=0). This is conservative (never understates tax) and the dropped leg is always surfaced for manual entry (B). Intentionally not worked around.
- **Cross-currency cost-basis conversion (Hard Trace — the €35M bug)**: a permuta's two legs are in DIFFERENT currencies — you acquire a coin paying coin X and dispose of it receiving coin Y (e.g. buy USDC paying EUR, sell USDC for BTC). The #219/V2422-20 FCY rule (`fifo.ts:disposalEur`) converts a disposal's cost AND proceeds at the SALE-date rate — correct ONLY for a same-currency security (buy USD stock, sell USD stock), where it strips the buy↔sale FX drift into the FX engine. For a permuta `lot.currency !== trade.currency`, so converting the (EUR-denominated) `costBasisFcy` by the SELL coin's rate multiplies a €277 cost by BTC's €78,890 price → a €21.9M phantom cost basis (real file: total adquisición €35,138,417, fake −€35,089,048 loss). **Fix**: `disposalEur()` keys on `lot.currency === trade.currency` — same → sale-date rate on both legs (V2422-20, unchanged); different → cost at the LOT's own acquisition rate (`lot.ecbRate` = real EUR paid, Art. 35.1), proceeds at sale rate, gain = their difference. **This was unmasked, not caused, by the v0.48.5 "Buy Crypto With Fiat" fix**: before it, those coins had no lot and hit the cost-basis-0 "sin lotes" path (couldn't explode); giving them lots surfaced the latent #219 mismatch. Only the two lot-consuming paths (long disposal + option-exercise underlying delivery) carry a non-zero cross-currency cost; short/expiration paths have one zero leg so they're already rate-correct.

### Binance "Transaction History" CSV — operation taxonomy (Hard Trace)
The Binance "Generate all statements" export (`User_ID,UTC_Time,Account,Operation,Coin,Change,Remark`) is a balance-change journal, NOT a trade list. `src/parsers/binance.ts` (`parseBinanceTxCsv`) classifies each `Operation`:
- **Trades (permutas / buys / sells)**: `Binance Convert`, `Buy Crypto With Fiat`, `Transaction Sold`+`Revenue`, `Transaction Buy`+`Spend`, `Small Assets Exchange BNB` (dust). Each crypto↔crypto leg-pair emits BOTH a SELL (given-up coin) and a BUY (received coin) so the received coin gets a FIFO lot. **Fiat-leg fix**: if one leg is genuine FIAT (`isFiat()` — EUR/USD/etc, NOT stablecoins), emit a single normal trade in that fiat currency, never a CRYPTO disposal of EUR (that caused "Venta sin lotes: EUR"). Stablecoins (USDT/USDC) ARE crypto → still permutas. A swap of one fiat for another (EUR→USD Convert, a fiat-for-fiat Strategy pair) books nothing, because the FX engine reads only cash trades; `binance.fiat_conversion_not_booked` names its rows. Booking it as an FX event is a design decision still open. **Dust** pairs dust rows and their BNB rows within ±1 s (not the exact `UTC_Time` string, which lost a BNB row 1 s later and its dust disposal); a dust row with no BNB row is named by `binance.unpaired_leg`; when the BNB rows are fewer than the dust coins, or several coins fall back from the Remark to file order, `binance.spot_cost_split` names the window. Leftover BNB rounding rows stay dropped.
- **`Buy Crypto With Fiat` (Hard Trace)**: the EUR/USD-funded card/balance purchase (crypto leg + negative fiat leg, ±1s apart). It is a paired-leg swap exactly like `Binance Convert` → both live in `TX_CONVERT_OPS` and route through `netLegs`→`pairAndEmit`→`emitCryptoSwap` (which emits a single fiat-priced BUY). **Symptom if unhandled**: the op fell through every handler, so the acquired coin got NO FIFO lot while later disposals still fired → a burst of phantom `fifo.sell_without_lots` ("Venta sin lotes: BTC … coste base = 0"). Real file: one `Buy Crypto With Fiat,BTC,0.0269` (€2499) caused 25 phantom BTC errors. Window grouping keys on `r.operation === start.operation` so a Convert and a fiat-buy in the same second never cross-mix. **Per-Remark sub-grouping (load-bearing)**: fiat-buys are ALL funded in the same coin (EUR/USD), so two buys in one second would net into a single fiat leg → `pairAndEmit` sees 1 sell vs N buys and silently DROPS all but one coin's lot (re-creating the phantom error). Each purchase carries a unique funding-wallet `Remark` (`Via CashBalance - Wallet/N…`) shared by both legs, so step 4 sub-groups fiat-buy windows by `Remark` before netting. `Binance Convert` legs have an EMPTY remark → its whole-window netting is deliberately left on the original path (NOT sub-grouped), provably unchanged — never route Convert through the per-Remark split (some Convert exports may carry mismatched remarks that would wrongly split a single conversion).
- **Plain SPOT trades (Hard Trace — the ~€200-cost bug)**: the OLDER "Generate all statements" vocabulary uses bare `Buy`/`Sell`/`Fee` (the spot-market trade legs) and `Sell Crypto to Fiat` (the cash-out), DISTINCT from the `Transaction *` Strategy vocabulary. A spot trade is a same-timestamp group: `Buy <received +>` + `Sell <given-up −>` + optional `Fee`; a `Referral Commission` may share the timestamp but is income (consumed by phase 2 first). **Symptom if unhandled**: these ops were in NO op-set → dropped; a user's 2021 spot buys created no FIFO lot, so 2025 sells fired `fifo.sell_without_lots` and the acquisition cost collapsed (real file: ~€200 vs ~€2000+ real, 4 "sin lotes" on one day). **Fix (phase 6, `SPOT_TRADE_OPS` + `emitSpotTrades`)**: pair by SIGN (NOT op name — `Sell` is the given-up leg of both a buy and a sale), via `netLegs`→`pairAndEmit`→`emitCryptoSwap` (same path as Convert: fiat leg → single fiat-priced trade; crypto-only → permuta). Runs AFTER income so same-second commissions aren't swept. `Commission History` added to `TX_INCOME_GENERAL_OPS` (base general 0304). `Sell Crypto to Fiat` carries a unique wallet `Remark` per cash-out → sub-grouped by a namespaced Remark key (`scf:<remark>`) so two same-second cash-outs of different coins don't net their EUR together, and an empty cash-out remark can never collide with bare Buy/Sell (`spot:`). **Lot-drop guard (load-bearing — the real file HAS this case, e.g. ADA+BTC bought in one second both paying EUR)**: bare Buy/Sell have an empty remark, so two DIFFERENT coins bought in the same second sharing one fiat would let `netLegs` merge the two EUR sells → 1 sell vs N buys → `pairAndEmit` silently DROPS a coin's lot (the very phantom this parser prevents). `emitBareSpotGroup` therefore detects >1 distinct received coin against a single fiat leg and pairs each bought coin with its own fiat row BY ORDER (the export lists N buys against N sells), never dropping; same-coin multi-fills still net cleanly into one lot. The per-coin fiat split is approximate only when order-to-order linkage is absent (rare), but the aggregate is exact and no coin ends with cost basis 0. **Fees**: a fee in an ECB-resolvable coin (fiat/stablecoin) is attached as commission (Art. 35: buy fee→cost, sell fee→proceeds); a fee in a non-resolvable coin (third-coin BNB, or the bought alt itself) has no rate and is sub-cent → dropped as dust (BNB-fee precedent). Each fee row goes once to the order the file writes it beside (`tieFees`, spot and Strategy alike): a fee in a coin only one order of the window takes goes to it; with two or more such orders, the nearest leg rows before and after the fee must belong to one of them. Otherwise the fee is deducted from no order (conservative) and `binance.fee_unassigned` names it. Before, the last spot trade of a second took every fee, every Strategy pair took the first fee row of its coin, and a fiat-for-fiat Strategy pair put its fee on an earlier, unrelated trade. Exact-string matching keeps `buy`/`sell`/`fee` distinct from `transaction buy`/`transaction sell`/`transaction fee` — never use `includes()`.
- **±1s grouping window**: Convert-style legs are frequently 1 second apart (≈half in real data). Rows are grouped within a ±1s window with a single-consume `parsed` flag; net per-coin to cancel intra-account split rows. A coin with rows of both signs that net to exactly zero in one Convert or fiat-buy window is no split row but a round trip (BTC → ETH and ETH → BTC within 1 s): netting dropped every coin and both disposals vanished with no word, so `markRoundTrips` names each of its rows by `binance.unpaired_leg` and books nothing for that coin, as which row belongs to which order is a guess (#467). **Straddle (window measured from its first row)**: when the next trade starts in a window's last second, its first leg lands in this window and its counterpart one second later. Strategy hands every unpaired Sold/Revenue/Buy/Spend leg back (`parsed = false`) for a later window, and a leg nobody pairs is reported as unhandled, never dropped silently. Convert and Buy Crypto With Fiat (`trimStraddle`) reason by sign, because Binance lists the two legs in either order: when the rows at +2s are one-sided (only received or only given-up) and nothing at +3s has the sign they lack, the coins at +1s with that sign go to the next window, provided what stays is still a complete conversion. A single conversion whose given-up coin is split across two rows 1s apart still nets as one, and a next conversion whose counterpart sits at +3s keeps its own legs. A netted Convert leg left without a counterpart is handed back (`parsed = false`) like a Strategy leg, so it is paired later or reported, never dropped. Chains of three or more conversions each 1s apart are not untangled.
- **Income** → `CashTransaction{type:"Crypto Reward Income"}` with `taxBucket`:
  - `"ahorro"` (rendimiento capital mobiliario, Casilla 0027): `Simple Earn Flexible Interest`, staking rewards. DGT V1766-22, Art. 25.2/43.1.
  - `"general"` (ganancia patrimonial NO derivada de transmisión, base general, Casilla 0304): airdrops (`HODLer`/`Launchpool`/`Token Swap`/`Crypto Box`), `Referral Commission`, `Strategy Trading Fee Rebate`. Art. 33.1; DGT V1948-21. **MUST NOT** go through interest/0027 (wrong base & rate) nor into `totalSavingsBase`/casillas.ts.
  - A negative income row (a reward taken back) books nothing and is named by `binance.income_negative` (coin, operation, change, time): DeclaRenta does not know which reward it cancels, so it makes up no disposal, and the reward's income and lot stay as they were. Kraken (`kraken.income_negative`) and Coinbase (`coinbase.income_negative`) do the same.
  - Each income reward valued at receipt-date EUR ALSO creates a tax-neutral synthetic BUY lot (`synthesizeRewardLots` in report.ts) at that EUR value, so a later sale isn't double-taxed (Art. 35.1). A BUY is never taxed by FIFO (only SELLs create disposals).
- **Skipped (non-taxable)**: `Simple Earn * Subscription/Redemption` (principal moves, not disposals — only the Interest is income), all `Transfer Between *`, `Deposit`/`Withdraw`, margin loan/repayment, `Copy Portfolio (Spot) - Create/Close` (principal moves between Spot and the "Spot Copy" sub-account — each coin nets to zero across the two legs; the lead trader's mirrored fills, if any, arrive as their own `Transaction *` rows — the skip assumes the legs are balanced, which holds in real same-timestamp exports), `BNB Fee Deduction` (sub-cent BNB fee dust). In `TX_SKIP_OPS`. **Accepted tradeoff**: paying a fee in BNB is strictly a micro-disposal of BNB (tiny Art. 33/37 gain/loss) — we omit it as immaterial dust, so the BNB lot balance is negligibly overstated. Valuing it would need a BNB price the tool deliberately never fetches (no-oracle/privacy policy), so skipping is the pragmatic call.
- **EUR_Value column** (optional, e.g. user-added): read into `FlexStatement.manualRateHints` and merged UNDER explicit user manual rates in report.ts (`mergeManualRateHints`). An explicit broker EUR value is authoritative even when `0` (Binance reports sub-cent micro-rewards as `0.0` — value at zero, don't warn). `merge.ts` must carry `manualRateHints` through (it's easy to forget — both web and CLI route through `mergeStatement`).
- **Validated** against a real 6000-row file: 44 FIFO errors + 66 unvalued → 0 unvalued, full capital-gains/income computed. Remaining "lotes insuficientes" are genuine data-window gaps (coin acquired before the export's date range) + Simple-Earn compounding dust (≈1e-7 units), both immaterial and conservatively warned.

### Dividend Grouping by Issuer (presentation-only)
- `groupDividendsByIssuer(entries)` in `generators/casillas.ts` aggregates per-payment `DividendEntry[]` into one `IssuerDividendGroup` per **issuer + source country** — the layout of brokers' fiscal certificates and the AEAT "Alta Capital mobiliario" form (one record per company with annual totals). Used by the Casilla 0029 detail card (web, with collapsible per-payment drill-down), CSV (a separate `# DIVIDENDOS POR EMISOR` section — the per-payment `# DIVIDENDOS` section is kept unchanged so neither is double-summed), and both PDFs.
- **PRESENTATION-ONLY, load-bearing invariant**: it is a pure render-layer helper (like `computeCasillaBlocksWithFx`), never stored on `TaxSummary`. `grossIncome` (Casilla 0029) and `calculateDoubleTaxation` (Casilla 0588) are computed from the raw per-payment `entries` independently, so `Σ group.grossTotalEur === grossIncome` exactly. Do NOT re-derive tax figures from the groups, and do NOT touch `dividends.ts`/`double-taxation.ts`/`report.ts` reduce.
- **Key** = `(isin || symbol || description) + withholdingCountry`. Country is in the key so each group maps 1:1 to a 0588 country line (a rare same-ISIN/two-country case shows as two blocks — honest and reconcilable, never a single block mixing countries). Empty-ISIN issuers fall back to symbol/description so distinct coins don't merge. Mixed currencies within a group → `currency: "—"`. Grouping runs on the already-titulares-split `report.dividends.entries`.

### Spanish Tax Law References
- **Art. 37.2 LIRPF**: FIFO mandatory for homogeneous securities
- **Art. 33.5.f/g LIRPF**: Anti-churning rule — losses blocked if the same security is repurchased within 2 calendar months (letter f: admitted to trading on a regulated market of the European Economic Area, Norway, Iceland and Liechtenstein included, or on a third-country market the European Commission declared equivalent) or 1 year (letter g: admitted to neither: unlisted shares, OTC-only securities, shares listed only on a third-country market with no equivalence decision). DGT V0778-25 (binding, 05/05/2025) applies letter f to the equivalent markets while the decision stands. The MiFID II decisions in force are Implementing Decisions (EU) 2017/2320 (US: NYSE, Nasdaq and the other SEC national exchanges), 2017/2318 (Australia: ASX, Chi-X Australia) and 2017/2319 (Hong Kong: SEHK); Switzerland's (2017/2441, 2018/2047) covered only 24/12/2017-30/06/2019, and the UK was EU law until 31/12/2020 and has none since. The EMIR art. 2a decisions 2016/2273 (Toronto, TSX Venture, Aequitas Neo), 2016/2271 (Tokyo) and 2016/2270 (Singapore) also declare markets equivalent to a regulated market, and V0778-25 accepted that kind of decision for CME: those stay at 2 months, flagged open. So never write the 1-year test as "not on an EU regulated market", never present a US, Australian or Hong Kong listing as a DeclaRenta deviation, and never list Toronto or Tokyo as settled 1-year markets. The window per ISIN comes from the user's value, else IBKR's listing exchange (London Stock Exchange from 2021, SIX, OTC Markets…), else 2 months with an ISIN (#452; see the Hard Trace below). Crypto is no «valor o participación» (DGT V0648-24, V0525-25): it falls under art. 33.5.e («elementos patrimoniales»), and the engine applies the year after the sale only (33.5.e, #457; see the Hard Trace below). `tests/i18n/guide-consistency.test.ts` pins this wording in the docs and the 5 locales
- **Art. 80 LIRPF**: Double taxation deduction — lesser of foreign tax paid or Spanish tax due
- **Art. 26.1.a LIRPF**: Only custody/administration fees are deductible from capital income. Margin interest is NOT deductible — shown as informational only.
- **Casillas**: 0327-0328 (capital gains), 0029 (dividends), 0027 (interest income), 0588 (double taxation). Real casilla 0032 = insurance income (Art. 25.3), not broker margin interest.
- **Savings brackets (2025+, Ley 7/2024)**: 19% (0–6k), 21% (6k–50k), 23% (50k–200k), 27% (200k–300k), 30% (>300k)

### Anti-Churning Total-Sale Carve-Out (Hard Trace — issue #249)
- **DGT V3282-18 situation 1**: when a loss sale leaves **zero** homogeneous shares in the taxpayer's patrimony, the loss is fully deductible. The engine must not count the very pre-sale lots FIFO just sold as surviving "repurchases".
- **Implementation invariant** (`src/engine/wash-sale.ts`): post-sale repurchases remain uncapped and block normally; pre-sale absorption is capped by `holdingAfter = max(0, net BUY/SELL position after the sale date)`, per purchase since #454 (each counts only its shares among the newest `holdingAfter`). Absorption runs once per (key, sale day) over the day's quantity, so a single SELL split across lots cannot over-block. Forward/reverse splits must be applied to this cap and to later pending-loss release proration so pre-split buys, post-split disposals, and pending-loss releases are all compared in the relevant sale's share units.
- **Do NOT replace this with a naive total-sale shortcut**. `buy 100 → sell 100 at a loss → rebuy 100 within the window` is still a genuine wash sale because the post-sale rebuy remains after the loss sale.
- **Single-year limitation**: if prior-year holdings are absent from the input, `holdingAfter` can understate the real position and is clamped at zero. This is the same data-window limitation as other FIFO paths; do not invent prior holdings inside the anti-churning detector.

### Anti-churning release only on a «transmisión definitiva» (Hard Trace — issue #451)
- **Trap**: up to 0.66.5 a blocked loss was keyed on the repurchase's buy date and released as soon as a disposal sold that lot, without checking the sale's own window. Sell A at −20, rebuy B, sell B at −5, rebuy C: 2025 deducted 20 that the DGT keeps deferred (V3282-18 «deben ser también definitivas … con independencia de que determinen ganancias o pérdidas», AEAT Manual IRPF 2025). The lot key also orphaned losses: V1760-23 left 200 pending forever, V0046-20 never released 1,933.30 because FIFO sold older lots.
- **Model** (`src/engine/wash-sale.ts`): a per-key FIFO queue of pending losses `(qty, eur, time)`, counted in the absorbed shares of the loss sale, split-adjusted at release. The unit is one (key, sale day), because FIFO splits a sale into one disposal per lot and same-day sales have no intraday order. Its loss lots, and its gain lots while losses are pending, absorb unused in-window rebuys with the same BLOCK rules (the DGT's pick order of #454, sale-day buys included) and use them up (V0248-18). The absorbed shares go to the loss lots first, newest acquisition first, then to the gain lots: the deductible part is the first-acquired shares (V0913-08 «atribuible a las acciones adquiridas en primer lugar», V1294-22), and a loss lot in a sale with a net gain stays blocked (V0279-25). Each disposal's `qty − absorbed` are definitive shares: each releases one pending share's loss, oldest first, into its `reintegratedLossEur` (V0571-21, V0754-26), whatever lot FIFO sells. A sale day with no absorption that leaves no shares releases everything left (V1760-23 «que le resten»); "no shares" must hold in the trades AND in FIFO (`getRemainingLots()` plus the disposals' holding spans), or scrip, merger, spin-off and reward shares would be ignored. A loss sale's own blocked part joins the queue after its release; the same absorbed shares block it and keep the old losses pending, never counted twice (V0913-08). `blockedLossEur`, `reintegratedLossEur`, the invariant `0 ≤ blockedLossEur ≤ |gainLossEur|` and the fiscal formula `net + blocked − reintegrated` are unchanged.
- **Do not**: re-key the release on lots, roll the deferral onto the next rebuy (the issue's proposal: worse than before on V0571-21, −533.33 against the DGT's −1,166.67), put the carried loss into `blockedLossEur` (double counts, breaks the invariant), let a gain lot with nothing pending use a rebuy (it has no definitive test to run; consuming would free a later loss the rebuy blocks), or walk a sale's lots one by one in FIFO order for the absorption (the older gain lot then takes the rebuy and the newer loss lot escapes the block: 750 deducted a year early in the mixed-lot test).
- **Known gap** (in the design doc): V2481-20 gives 1,751.73 against the DGT's 1,767 (`it.fails` on the DGT's figure): the 23/04 sales need 40 of the 1,900 bought on 06/05, so 20 of the 1,880 sold on 29/04 are definitive and release 15.27; the DGT does not count those 40. The pick order (#454) and the sale-day rule do not change it.
- **Only held shares, only real exits** (late review of #455): a short cover (`isShort`) buys back shares sold short, so it is never a «transmisión definitiva»: it seeks no rebuy as a gain lot, releases nothing and is no exit (its own loss still blocks). Its buy is no repurchase either: the covered shares go straight back to the lender and never stay in the patrimony, so `detectWashSales` indexes a `C`/`C;O` BUY only for what is left after FIFO's short disposals on that (key, day), and a `C` buy with no open short not at all (FIFO books nothing for it; `fx-fifo.ts` skips cover buys too). The day's covered shares go to the cover buys in FIFO's processing order (`compareFifoTradeOrder`, exported from `fifo.ts` and used by both): FIFO runs a `C;O` buy before a `C` buy, so walking the file order counted an orphan `C` buy listed first as a repurchase (late review of #459). FIFO runs the day's SELL `O` rows between the two, so the covered shares are split by the short disposal's `acquireDate`: a `C;O` buy takes only shorts opened on an earlier day, a `C` buy takes what is left of those and then the same-day ones. A single day budget gave a flip's same-day short to the `C;O` buy and under-counted the repurchase (second review of the #459 follow-up; a fuzzer of 8,000 flag-consistent runs now matches FIFO's kept shares on every buy day). Without this a cover buy blocked a loss that nothing released once the position stayed flat (Σ blocked ≠ Σ released; the long/short property test pins it). A zero-share disposal (FIFO books a 0-quantity SELL row with no lots) is skipped, or it drained the queue as a total exit. The holding spans of the total exit start at `entryDate ?? acquireDate`: FIFO sets `entryDate` on spin-off lots and on lots of a merger into a new ISIN, and their disposals, which keep the parent's tax `acquireDate` and otherwise look held before the corporate action. A TC row that names no new security is booked as a merger of the ISIN into itself: it must keep each lot's entry date, or held shares looked bought on the TC date and an earlier sale became a total exit. Never reuse `acquireDate` for this (it is the Art. 37.1 date the gain and the hand-out order read). The total exit's remainder goes to the day's last long sale, never to a same-day short cover. The release walks the queue with a cursor (10,000 one-share lots: 20.6 s → 0.2 s, bound in the engine test).
- **Window past the loaded data**: neither BLOCK nor RELEASE can see a buy after the upload ends. One shared warning, `report.antichurning_window_past_data` (5 locales), lists the year's sales whose window ends after the last date the upload covers (`statement.toDate` or the last trade of ANY security, not of that security: a final exit always has no later trade of its own) and whose result a later buy could change (a loss not fully blocked, or a release). Nothing is withheld. With several merged brokers (`brokerSource`, and `holdingsBySource[].brokerSource` for each file's statement end) a security is covered only up to the earliest end among the brokers that trade it, or a DEGIRO file ending on its December loss hid behind an IBKR statement running to the next year. A broker with a statement end and no trades counts as one of the brokers too (late review of #459). From tax year 2024 a window ending after 30 June of the next year (the filing deadline) gets `report.antichurning_window_open_at_filing` instead: it is still open when the user files, so it never says "if you did not buy, the result is correct" and points to an autoliquidación rectificativa.
- **Migration**: a year filed with 0.66.5 or earlier may have deducted a loss early; the new engine releases it later. The Renta Web guide (`guide_rw.blocked_losses_hint`, 5 locales), docs/casillas.md and docs/faq.md tell users not to deduct it twice or to correct that year, and, the other way round, that a loss the new engine releases in an already filed earlier year (V0046-20) can be claimed by correcting that return. Whenever a user corrects an earlier year to claim a loss (this case or #453's), they must also check the later years already filed and remove that same loss where the old version released and they deducted it, so it is never deducted twice (review of #453; same sentence in the guide, casillas.md and faq.md). The procedure is by year (AEAT Manual Renta 2025, «la autoliquidación rectificativa como sistema único … desde el período impositivo 2024»): 2024 on, an «autoliquidación rectificativa» in both directions; 2023 and earlier, a complementaria to pay more or a solicitud de rectificación to claim. Never write "file a complementaria" alone. Byte-identity on the fixtures: only `trading212-v2-sample.csv` 2025 (reintegrated 4.86/5.07 → 0, its 05-27 gain sale has an unused 05-23 pre-sale rebuy) and `binance-v2-sample.csv` 2025 (1.6e-6 EUR, the 04-09 sale is rebought on 04-11) move.
- Pinned by `tests/integration/antichurning-definitive-e2e.test.ts` (one block per consulta through `generateTaxReport`, all three FX methods on the issue example, and a seeded property Σ blocked = Σ released over closed positions, summed as Decimals before rounding, the mixed-lot and scrip/merger regressions, the short-cover (with FIFO's same-day cover order and the total exit beside a cover), zero-share, spin-off and merger entry-date (with the same-ISIN TC row) and window-past-data (with a statement-only broker) blocks; `tests/i18n/guide-consistency.test.ts` pins the partial-release and correction wording in the 5 locales and the docs; controls: definitive = whole quantity → 18 red; no total exit → 4 red; gain sales always absorbing → the guard in `tests/engine/wash-sale.test.ts` goes red; no FIFO check on the total exit → the scrip and merger tests go red).

### Anti-churning pick order (Hard Trace — issue #454)
- **Trap**: up to 0.66.13 `detectWashSales` took post-sale buys first, then pre-sale buys newest first under one `holdingAfter` cap that a used buy did not reduce. A sale then took the next sale's rebuy, and an old lot FIFO had already sold could still block. V0248-18: 29/05 released 400 (2017 fiscal 500, DGT 900); V0754-26 with each rebuy before its sale released 385 in 2025 (DGT 0); V1760-23 and V3282-18 matched only by chance, with other purchases than the DGT names.
- **Rule** (derived from the purchases the consultas name; `src/engine/wash-sale.ts` ABSORB): (1) oldest unused purchase first, so pre-sale before post-sale (V3282-18: 26/03 ← 20/03, not 24/03 or 28/03; V0248-18: 25/04 ← 3,000 of the 18/03 lot, «5000 acciones (2.000, 3.000)»); (2) a used purchase is out (unchanged); (3) a pre-sale purchase counts only for its shares still held after the sale: walking the pre-sale buys newest first, each holds what is left of `holdingAfter` (V1760-23: 10/05 ← 10/06, because the 06/05 shares are used and the 04/05 shares sold); (4) a purchase only partly held is the lot the sale transmits and goes last, after the post-sale buys (V3282-18: 20/02 ← 15/03, not the rest of 15/02; V1760-23: 05/05 and 09/05 ← 06/05, not the rest of 04/05). It still counts (situation 3; the #453 exception lifts steps 1 and 4). Steps 3 and 4 work per buy day, not per row: a day's rows share one held count, and a partly held day goes last with all its rows (DEGIRO lists one order as several fills; per row, buy 100 / sell 50 / buy 50 / sell 50 gave −40 with fills of 60 + 40 instead of −200).
- **Do not**: go back to post-sale first (V0248-18, V0754-26 break), walk pre-sale oldest first without the held-shares cap (old sold lots block: V1760-23 19/07 stops being definitive, and V2481-20 jumps to 1,767 for the wrong reason), or take the partly held lot before the post-sale buys (V1760-23 and V3282-18 picks break; with the #453 exception unverified V1760-23's figures break too). Or skip the sale day in the walk while `holdingAfter` counts its buys (the stand-in up to the #454 follow-up, see below).
- **Sale-day buys count for their own held shares** (#454 follow-up, 2026-11-19): FIFO sells the oldest shares first, so the shares bought on the sale day are the newest held after it. The walk starts at the sale day (`preTo = firstIndexAfter(buyEvents, sellTime)`), so the day's buys take the first part of `holdingAfter` and are used up like any purchase: after the older held days (oldest first), before the post-sale buys, or last when only partly held (step 4: the sale transmits part of them). The DGT counts a sale-day buy as a rebuy (V0571-21: the 7,000 bought on 11/08 make that sale not definitive). Crypto never reaches it: its window starts at the sale (`windowStart = sellTime`), so `preTo` stays at `windowFrom` and the walk is empty (art. 33.5.e, «año siguiente a la fecha»). A sale-day buy is still a second purchase for the #453 count. A split on the sale day puts the day's buys and the sale in the same units, as `holdingAfter` does. Figures: the review's example 90 (buy 100 on 01/03 and 40 on 05/03, sell 100 at a loss and buy 50 on 10/03), V2481-20 1,751.73 with the trail 20/04 ← 20/04 (was ← 14/04) and 22/04 ← 21/04, and every other consulta unchanged (V0571-21 −1,166.67, V0248-18 900, V0754-26, V3282-18, V1760-23, V0046-20, V0913-08, V1294-22).
- **Trap: the stand-in** (up to 0.66.13 and the #454 lane): the walk skipped the sale day, but `holdingAfter` counted its buys, so their held shares went to the newest earlier buy day, an older lot even if FIFO sold it. It missed the rebuy when no unused older lot was in the window (buy 100 on 01/12/2024, sell them on 10/03/2025 at −100 and buy 50: 0 blocked, DGT 50; or with 02/03 used by a 03/03 sale: 10/03 blocked 0 and released 100, fiscal −200, DGT −100; and a sale rebought the same day counted as definitive: the V0571-21 layout without its unused pre-sale buy released 50, DGT 0). The sale-day shares were used twice (sell 25 more on 20/03 at a loss: blocked 25, DGT deducts and releases 25). And the stood-in lot was only partly held, so it went after the post-sale buys (buy 100 on 01/03, sell 100 on 10/03 at −100 and buy 50, buy 100 on 15/03, sell 50 on 20/03 at −50: fiscal −100, DGT 0). **Do not** take the sale-day buys off `holdingAfter` instead (a review's proposal): it gives 40 instead of 90 on the example, V2481-20 1,088.08 and V0571-21 −1,500.
- **Migration**: a loss sold and rebought on the same day could be deducted by 0.66.13, although the law defers it; the new engine blocks it, or keeps an older loss pending. `degiro-transactions-sample.csv` 2021 moves in all FX methods: THETA buy 2 and sell 1 on 14/04 with nothing held before is now one purchase the CSV cannot prove, so the #453 fail-safe blocks 49.02 (24.51 with two owners) and adds `report.antichurning_single_purchase_unverified`. No other fixture moves (byte-identical with `fxTrace` on, 5 option sets). docs/casillas.md tells users to correct a filed year that changes (2024 on: autoliquidación rectificativa; 2023 and earlier: complementaria if it comes out to pay), in the securities warning box. That box is titled «0.66.13 o anterior» and names the version in each paragraph (#451 notes say 0.66.5), because a user skips a box whose title leaves out the version they filed with; `guide-consistency.test.ts` fails when a box names a version newer than its title.
- Pinned by `tests/integration/antichurning-definitive-e2e.test.ts` (V0248-18 and V0754-26 in all three FX methods, the DGT's repurchase dates on V3282-18, V1760-23 and V2481-20, a held-shares block: buy 100 + 100, sell 100 at −100, sell 50 at −50 → the second sale is definitive, −100; and the same buy as one row or two same-day rows → −200 both) and `antichurning-single-purchase-e2e.test.ts` (the DEGIRO one row vs two fills with one «ID Orden», no one-purchase mark), and `antichurning-same-day-held-e2e.test.ts` (sale-day buys through the IBKR and DEGIRO parsers in all three FX methods: the review's example 90, a sale larger than the earlier holding 30, a definitive test kept pending by a sale-day rebuy, the three stand-in gaps on the DGT's figures, the #453 exception with a sale-day buy, and the committed DEGIRO fixture's THETA block); `tests/engine/wash-sale.test.ts` pins a same-day rebuy in another account, a split on the sale day, the definitive test with a same-day rebuy and the crypto/letter-g mirror. ### Crypto anti-churning = art. 33.5.e, the year after the sale only (Hard Trace — issue #457)
- **Trap**: up to 0.66.13 every CRYPTO sale got the window of an unlisted security, 12 months before AND after (`windowStart = addMonths(sellDate, -12)`). A crypto buy before the loss sale that was still held after it blocked the loss: buy 1 BTC on 01/12/2024 (200), buy 1 on 01/03/2025 (100), sell 1 on 01/06/2025 for 100 → 100 blocked, 0 deductible. The same pre-sale pass ran in the #451 definitive test, so a buy before a LATER crypto sale kept an older loss pending (2026 released 0 instead of 100).
- **Law**: letter e (`elementos patrimoniales`) counts only a reacquisition «dentro del año siguiente a la fecha de dicha transmisión»; f and g need «valores» and count buys «anteriores o posteriores». Crypto is neither a «valor negociable» nor an art. 8 RIRPF «valor homogéneo» (V0648-24, V0525-25), the DGT applies letter e «y no las letras f) y g)» to dollars (V1613-25), Orden HFP/310/2023 files crypto under «otros elementos patrimoniales», and the AEAT Manual gives those «un año posterior a la transmisión». No consulta, TEAC resolution or ruling names crypto and art. 33.5 together: it is a firm deduction, not a holding, and the docs must say so. Never cite the Modelo 100 "has no crypto repurchase box" as support: it has none for shares either.
- **Fix** (`src/engine/wash-sale.ts`): `looksBack(assetCategory)` is false for CRYPTO, so the absorb window starts at the sale (`windowStart = sellTime`) and the pre-sale pass walks an empty slice (crypto has no total exit since the follow-up below). `windowMonths` stays 12, so the window end (sale + 12 months, end day included, `addMonths` clamps 29/02 → 28/02), `salesWithWindowPastData` and the 30 June open-at-filing split did not move. A same-day rebuy stays excluded («año siguiente a la fecha»).
- **Choices** (each in docs/casillas.md): same ticker on any exchange or wallet = same element (`CRYPTO:<SYMBOL>`; WBTC ≠ BTC); a swap leg that acquires the coin is a repurchase (permuta, V1149-18); partial reacquisition stays proportional; staking, airdrop and reward receipts are no repurchase (reward lots stay out of `washSaleTrades`, the less strict reading); every CRYPTO row is letter e (a security token cannot be told apart in an export).
- **Release = transmission of the rebought coins** (#457 follow-up, CodeRabbit on geiresx/DeclaRenta#16). The first #457 fix kept the #451 share-count «definitiva» queue for crypto, and with the look-back gone from it a sale of OTHER coins released the loss while the rebought coin was still held: buy 3 BTC in 2023, sell 1 on 01/06/2025 at −100, buy 1 on 01/07/2025 and 1 on 01/05/2026, sell 1 on 15/06/2026 (FIFO sells a 2023 coin) → 2026 released 100. Letter e: «se integrará cuando se produzca la posterior transmisión del elemento patrimonial»; AEAT Manual Renta 2025 («otros elementos patrimoniales»): when «se transmita el elemento patrimonial adquirido». No consulta names crypto and art. 33.5 together; this reads the statute and the Manual. **Model** (`wash-sale.ts`, `TieGroup`, `tiesByAsset`): each crypto block is tied to the coins of the rebuys that absorbed it, per buy day (`chunksOf`); the queue's RELEASE step and the TOTAL EXIT skip crypto. On each sale day the tied units leaving a buy day are `tied − cryptoHeldAfter(day)` (the day's REBOUGHT coins still held after the sale, from FIFO's `remainingLots` plus later disposals of that day, minus that day's reward coins: FIFO books a day's lots in input order, trades → reward lots → manual opening lots, so the held coins are that tail): the tied coins of a day go last. They release proportionally (`takeTiedUnits`, `shareOut` keeps the EUR parts summing exactly), even when the coin is bought again in the year after: letter e has no f/g «definitiva» test, and that buy blocks the new sale's own loss instead. Only crypto loss lots take a rebuy, so no gain sale uses one up. No total exit for crypto: selling out before a later rebuy transmits none of its coins. A crypto release is final, so it raises no past-data or open-at-filing warning by itself (`salesWithWindowPastData`); an open crypto loss still does. One fixture number moved: `binance-v2-sample.csv` 2025 releases 0.0000012 EUR (0.00 in every box) on the 09/04/2025 ETH sale of 0.002081 coins bought 25/02/2025, because 0.0015935 of them carried the 13/01/2025 loss of 0.00000307 and the 11/04 rebuy no longer holds that back. **Do not**: put crypto back on the share-count queue or the total exit, release on a sale of untied coins, roll a sold tied coin's claims onto the next rebuy (the first follow-up did, and its gain sale used up the rebuy: BTC −10 blocked on 02/06/2025, its rebought coin sold at +5 on 01/09, then a −1000 loss on 01/10 with a buy on 03/11 → 2025 deducted the 1000; letter e defers it), let a crypto gain lot take a rebuy, count a reward coin as a held rebought coin (a 0.5 ETH reward on the rebuy day held back half the release after the rebought coin was sold), or drop `remainingLots` from `buildCryptoDayHoldings` (without it a day's coins held are bought − sold by the trades). ### Anti-churning window per ISIN: 2 months or 1 year (Hard Trace — issue #452)
- **Trap**: up to 0.66.13 `windowMonths` gave 2 months to every security with an ISIN. A share listed only in London (sales from 2021), on SIX (from July 2019) or on OTC Markets is letter g: buy 01/02/2025 at 100, sell 01/03 at 80, rebuy 01/08 at 85 deducted −20 that the statute defers.
- **Law**: letter f needs admission «en alguno de los mercados secundarios oficiales» of Directive 2004/39 (now MiFID II, art. 94): an EEA regulated market or a third-country market with a Commission equivalence decision in force (V0778-25). One qualifying listing is enough. MTFs (AIM, BME Growth, Euronext Growth, Freiverkehr) are not regulated markets (V0422-09). The EMIR art. 2a decisions (Toronto, TSX Venture, Aequitas Neo, Tokyo, Singapore) lean letter f under V0778-25's CME passage, but no consulta covers shares: **open**.
- **Model** (`src/engine/antichurning-window.ts`): `collectIsinWindows` reads IBKR `listingExchange` from Trades and SecurityInfo (never `exchange`, the venue; crypto and the exempt categories never vote) and the user's `windowMonthsByIsin` (web panel «Plazo anti-churning por valor» in localStorage `declarenta_antichurning_windows`, CLI `--antichurning-1y` / `--antichurning-2m`; keys must pass `ISIN_SHAPE`, values exactly 2 or 12, built into a Map). `resolveIsinWindow`: the user's value wins; else 12 only when EVERY code of the ISIN in force on the sale day (`listingsOn`) is in `NON_EQUIVALENT_LISTINGS` and outside its `equivalent` spans on that day (LSE until 2020-12-31, EBS 2017-12-24..2019-06-30); else the old heuristic (ISIN → 2, none → 12). Unknown or misspelt codes get no vote, so they keep 2 months. **Dated votes** (`IsinWindow.votes`: code, conid, date): `listingExchange` is the contract's primary listing, so a code drops out on a sale day only when every row of the SAME conid naming it is older than that conid's latest row on or before the sale day (NYSE buy in February, PINK sale in March: only PINK counts, 1 year). A SecurityInfo row carries its conid and `asOf` = its statement's `toDate`, so last year's listing cannot outvote this year's trades but this year's can keep 2 months. `mergeTradeGroup` keeps the first non-empty `listingExchange` of an order's fills, and `listingExchanges` (every code) when the fills disagree; both vote. `LSEETF` is not listed (the big UCITS ETFs are on EEA regulated markets). Crypto stays 33.5.e (#457), whatever the user sets.
- **One map, three users**: `report.ts` builds the map once and passes it to `detectWashSales` (7th parameter: the block, the #451 definitive test, the #454 pick order) and `salesWithWindowPastData` (5th: the #462 past-data and open-at-filing warnings). Messages: `report.antichurning_one_year_ibkr` (warning, names each ISIN with its IBKR codes and the way back: mark 2 months), `report.antichurning_listing_open` (info), `report.antichurning_window_user` (info, the windows set by hand). `capitalGains.antichurningSecurities` lists each ISIN with a loss sale or a release in the year, a user value, or a sale with an IBKR 1-year reading on ANY sale day of the year (a gain sale can turn non-definitive under 1 year; SIX sold 01/11/2017 = 1 year then 27/12/2017 = 2 months keeps the row: reading only the last sale day dropped it, the warning and the panel's way back); every condition survives a toggle, so a row never disappears. - **Model** (`src/engine/wash-sale.ts`, `singlePurchase`): per (key, sale day), only where the pre-sale pass would take something (a dry run of `consume`), and only in the 2-month window (letter f: the doctrine states it there and nowhere for letter g). ### A trade row a parser cannot read is kept, never dropped or booked as a buy (Hard Trace — issues #466, #467, #468)
- **Trap**: up to 0.66.14 the parsers dropped a buy or sale row they could not read (`continue` on a missing date, ticker or ISIN, an unknown type, an empty amount), and several booked a row of unknown type as a buy: Freedom24 read every operation but `sell` as a buy, Kraken every type but `sell`, IBKR a missing `buySell`, Flatex the Nominal's sign, eToro any direction but `Short`. A dropped row hid a second purchase, so the #453 one-purchase exception went to "applied" and a loss was deducted with no proof; a row of unknown type booked as a buy gave FIFO a false lot (Kraken: gain 2000 instead of 1000). Revolut checked `FX Rate` before the row type and deleted a sale (net 550 → 0) or a dividend (0029 121 → 0) whose cell was bad, although only cash rows read it (#466).
- **Model**: a row that names a security and looks like a trade but cannot be read becomes `unreadableTrade` (`src/parsers/csv-utils.ts`): a `quantityUnknownTrade` with `Trade.unreadableRow` = security, date and the failing cell (`XYZ 20241202 [Type: "TRANSFER IN"]`). ### IBKR DateTime Format (Hard Trace)
- IBKR Flex Query dateTime fields use `YYYYMMDD;HHMMSS` format (e.g. `"20190916;130630"`), NOT `YYYY-MM-DD` or plain `YYYYMMDD`
- **Symptom**: `Error: Invalid time value` when processing dividends/interest, or silently wrong ECB rate lookups
- **Root cause**: Code using `dateTime.slice(0, 10)` gets `"20190916;1"` instead of a valid date — the semicolon is at position 8, not position 10
- **Fix**: Always use `normalizeDate()` from `dates.ts` which strips the `;HHMMSS` time component. Never use raw `slice()` on dateTime fields.
- **Safe pattern**: `slice(0, 8)` also works (extracts `"20190916"`) but `normalizeDate()` is preferred as it handles all formats
- **Files affected**: `dividends.ts`, `report.ts` used `slice(0, 10)` — `fifo.ts` was safe because it used `slice(0, 8)` + `normalizeDate()`

### IBKR Open Positions quantity (Hard Trace)
- IBKR writes the held quantity of an `<OpenPosition>` as `position`, not `quantity` (every real export in `tests/fixtures` has only `position`; `quantity` is the Trades attribute). Up to 0.66.13 `mapOpenPosition` read only `quantity`, so every real row read "0": the D-6 dropped every IBKR holding as "not long", the 720 tranches got 0 shares, and the #453 evidence could never pass. The parser reads `position ?? quantity` and marks a missing or non-numeric one `quantityUnknown`, with quantity "0" (never the raw text: `position=""` gave `""` and `new Decimal("")` crashed the D-6, review of #453). With "0" the 720 writes that holding with its value and 0 shares and the D-6 leaves it out of its positions list (it never lists a long one as a cancellation: `heldIsins` counts a `quantityUnknown` row as held unless its `positionValue` is negative, the 720's `isHeldSecurity` sign rule, so a holding in last year's D-6 is not reported sold, and a short one is cancelled in both forms; review of #453), so the parser adds one `parser.open_position_quantity_unknown` warning (5 locales) naming every such holding. The 720's cancellation (C record) keys on `positionValue`, not the quantity, so it is unaffected; the 721 has no previous-year logic. A Trade row gets the same treatment (`Trade.quantityUnknown`, `parser.trade_quantity_unknown`). With the Summary and Lot options both on, IBKR lists each holding as a SUMMARY row plus LOT rows; the parser drops LOT rows that have a SUMMARY row (`dropLotRowsWithSummary`). Pinned in `tests/parsers/ibkr.test.ts` (`ibkr-multicurrency.xml` through the D-6) and the #453 e2e (g) block.

### FOP/FSFOP Asset Category (Hard Trace)
- IBKR reports futures options on MEFF (Spanish derivatives exchange) as `assetCategory="FOP"` or `"FSFOP"`
- These must be added to `KNOWN_CATEGORIES` in fifo.ts, `WASH_SALE_EXEMPT` in wash-sale.ts, and `ASSET_LABELS` in web/asset-labels.ts (with its `asset.*` key in all 5 locales)
- FOP/FSFOP are derivatives → exempt from anti-churning (Art. 33.5.f only applies to homogeneous securities)
- They share option-like metadata (strike, expiry, putCall) — extend OPT spreads in fifo.ts to also match FOP/FSFOP
- **Symptom**: massive false blocked losses (~22K EUR) and 75+ "categoría desconocida" warnings
- **ISIN guard**: FOP trades on MEFF often have empty ISIN. The wash-sale matcher must skip disposals with empty ISIN to avoid false matches against unrelated securities

### FX Phantom Gains from Missing Prior-Year Lots (Hard Trace)
- If a user's Flex Query only covers the declaration year, prior-year FCY acquisitions are missing → no lots exist when the engine tries to consume them
- **Old behavior**: `costBasisEur = 0` → fabricated huge phantom profits (e.g. 48K EUR)
- **Fix**: When lots are missing (both "sin lotes previos" and "insuficientes" paths in fx-fifo.ts), set `costBasisEur = proceedsEur` → zero gain. The warning still fires so users know data is incomplete.
- **FX event sources**: explicit CASH conversions generate FX events, AND — since #239 — IBKR auto-convert (FXCONV/AFx) conversions are processed BY DEFAULT (they are real FCY→EUR conversions; IBKR does not round-trip on a stock sale, so the taxpayer genuinely holds the FCY). Securities trades do NOT generate implicit FX events — this avoids double-counting and phantom gains entirely.
- `isFxconv()` is RETAINED as the per-trade AFx detector and now drives an OPT-OUT (`ReportOptions.trackAutoConvert=false` / CLI `--skip-auto-convert` / web profile checkbox) that restores the old skip for accounts that genuinely round-trip. No global auto-convert detection (`detectAutoConvert()` stays removed, #171).

### ECB Rate Handling
- ECB publishes rates as "1 EUR = X FCY"
- We store the inverse: "1 FCY = X EUR" for direct multiplication with broker amounts
- Weekends/holidays: walk backward up to 10 business days
- Rate source: `https://data-api.ecb.europa.eu/service/data/EXR`
- **Early-January lookback (Hard Trace)**: `fetchEcbRates(year)` only fetches rates for that calendar year. Trades on Jan 1-2 trigger a 10-day lookback into late December of the *previous* year, but those rates won't exist in the map unless `year - 1` is also fetched. **`deriveEcbNeeds` (`src/engine/ecb-orchestrator.ts`, shared by web and CLI) adds `y - 1` for EVERY year in the set**, not only the earliest: a file with activity in 2023 and a dividend on 1 January 2025 needs late-December 2024 even though 2024 had no activity. This bug surfaces every time a new parser is added with sample data containing early-January trades.
- **Current-year rates are never cached**: the orchestrator memoizes past years per (currency, year), but the current UTC year's batch grows every business day, so it is refetched on every run.

### Monodivisa Mode
- **Three methods since #434** (`FxMethod` in `src/types/tax.ts`): `"multidivisa"` = «Criterio DGT (multidivisa)», the default and recommended; `"tradicional-divisa"` = «Tradicional con divisa» (next section); `"monodivisa"` = «Tradicional sin divisa (monodivisa)», this section. Use these exact names in UI, PDF, CSV (`Metodo_Divisa` row; the `Monodivisa SI/NO` row stays for one release), CLI help and docs. `reportOptionsForMethod(m)` (report.ts) maps a method to `{ skipFx, traditionalFx }`; `fxMethodOf(settings)` reads it back from `ReportSettings` (monodivisa wins over a stray `traditionalFx`). CLI: `--fx-method <m>` with choices; `--monodivisa` is an alias, and `--monodivisa` with `--fx-method` of another value exits 1.
- Chosen on the review step (`fxMethod` in the profile, with the `monodivisa` boolean mirror still written) + CLI `--monodivisa` (= `--fx-method monodivisa`). The web asks, and applies the saved method, when the upload has any non-EUR currency with an ECB rate, stablecoins included (`foreignCurrencies`, `src/web/fx-method.ts`); otherwise it runs the default. A trap: counting only fiat forced the default on a crypto-only USDT upload, where the saved monodivisa gives 190 instead of 90 on a BTC/USDT trade (`tests/web/method-stablecoin.test.ts`).
- When active: skips the FX FIFO engine entirely (`skipFx: true` in `ReportOptions`)
- `skipFx` ALSO sets `FifoEngine({traditionalCostBasis:true})` → a same-fiat FCY security's cost converts at the ACQUISITION-date rate (Art. 35.1), embedding the buy→sale FX drift in the stock line (the FX engine being off). Drift counted exactly once (stock line here, FX engine in default); capital gains deliberately DIFFER from the FX-on case — don't "fix" back to sale-date cost. Also affects option-exercise delivery + same-stablecoin permutas, and short closes, option expirations and option exercises/assignments (the open leg — short-sale proceeds, premium paid or received — converts at its own date's `lot.ecbRate`; on an exercise the strike leg uses the exercise date and `exerciseRate()` blends the two).
- Matches Autodeclaro/Taxdown ONLY in how shares are valued (buy at the buy-date rate, sale at the sale-date rate — the DGT fund method of V2324-10 / V0775-21 applied to shares). It is NOT full parity: it computes no currency result at all (Art. 33.1, timing Art. 14.2.e LIRPF), not even for the taxpayer's own USD→EUR conversions or broker AFx/FXCONV ones, while Autodeclaro documents a «Cash (Forex)» section for currency sales. UI text must say exactly that and send users who convert currency to «Tradicional con divisa» (same share valuation, keeps conversions) or the default (#230, #434). When monodivisa drops conversions in the report year, the info message `report.monodivisa_conversions_skipped` says how many.
- Warning text must say "distorsionar" not "infraestimar" — monodivisa can both understate (miss FX gains) and overstate (miss FX losses)
- Art. 80 double taxation deduction is subtly affected (lower `totalSavingsBase` when FX gains are skipped) — accepted known limitation matching competitors
- Cite DGT consultas specifically AND for what they actually say. V2324-10 is about investment funds in foreign currency (cost at the subscription-date rate, proceeds at the reimbursement-date rate, FX on the dollars deferred to their conversion); it is NOT a rule on FIFO for currency. No consulta applies FIFO to fiat currency (see the parking/ordering bullet below). The default mode's share treatment follows V1740-17 / V0282-22 / V2422-20; the official rate is the ECB's by Ley 46/1998 art. 36.

### «Tradicional con divisa» (`traditionalFx` — issue #434)
- **What**: the stock line of monodivisa (cost at the buy-date rate, `FifoEngine({traditionalCostBasis:true})`, also in the year-end replay) PLUS the FX engine, so 0328/0331 equal monodivisa's in every year and 1633/1637 tax the currency when it LEAVES the account: conversions, fees, interest paid, and dollars lost in a loss sale. `ReportOptions.traditionalFx` (`skipFx` wins); `new FxFifoEngine({ traditionalFx: true })` (the no-arg constructor is the default); `ReportSettings.traditionalFx: true` is written only when on, so default and monodivisa settings stay deep-equal. Everything is gated: default and monodivisa are byte-identical to before in every number (fixture JSON diff with `fxTrace` on, all 37 fixtures × 4 option sets).
- **The shift (V4r)**: a stock buy parks principal tagged with `buyRate` r_b. At the sale, a covered slice comes back at `r_lot + r_s − r_b` (the drift r_s − r_b is already inside the stock line), recorded in `FxLot.shifts`; a `null` (untracked) slice comes back at r_s; the profit at r_s. Each currency variation is declared exactly once, and a closed cycle totals EUR out − EUR in − income + fees (property test over random cycles). Never cite V0282-22 for the shifted principal (its text says otherwise). If `r_lot + r_s − r_b < 0`, the slice's own drift is booked at the sale (lost-dollar row) and it comes back at r_s carrying only this sale's shift (the guard row already reports the older ones) (negative-cost guard, trigger `stock_sale_guard` on the disposal and its trace row, its own `fx_traditional_guard` note).
- **Lost dollars, per mode**: in THIS mode a loss sale books the unreturned principal as an `FxDisposal` with `trigger: "stock_sale"`: proceeds `x·r_b`, cost `x·r_lot` (the drift between buying the currency and buying the shares), rows with gain 0 skipped. A sale with negative net proceeds (commission above the gross) is not dropped: the whole principal is lost and the extra `|proceedsFcy|` consumes pool lots as a fee (`trigger: "commission"`). This departs ON PURPOSE from the default's "loss sale = ZERO in 1633/1637" rule (carry-basis section): without it f, f2, l, z0 and r break the invariant. Anchor: V0775-21 3º and V2324-10 book that drift for FUNDS in the year of the sale. The default keeps the zero rule.
- **Sold in another currency** (same ISIN on another listing; the stock FIFO matches lots by ISIN): `FifoEngine({ markLotCurrency: true })`, set whenever the FX engine runs (this mode and, since #441, the default; never monodivisa), writes `acquireCurrency` on such a disposal, in `consumeLots` and in `consumeLotsForExercise` (a EUR option exercise or assignment delivering USD-bought shares: without it the USD stayed parked, 100 on 200); never on a same-currency or lot-less delivery. The lot's currency's parked principal is released at the sale, each covered slice booking its drift `x·(r_b − r_lot)` as an `FxDisposal` with `trigger: "stock_sale_cross"` (not lost dollars: no `lost_dollars` message); the sale's currency, if foreign, enters its pool whole at the sale rate (`profit` row), never unparking that currency's principal of the same ISIN. CodeRabbit's case: fund 1000 USD for 800, buy at 0.90, sell for 1000 EUR = stock 100 + currency 100. A trap: the `currency === "EUR"` skip left the USD parked forever (100 on 200), and a EUR lot sold in USD unparked the USD lot's principal. The default does the same since #441 (next bullet). Monodivisa computes no currency by design (100). Pinned by `tests/integration/fx-traditional-cross-currency.test.ts`.
- **Dating (R0)**: every FX event goes on its TRADE date (conversions, stock buys, stock sells), and a cash row (dividend, interest, fee, withholding) on its `dateTime`: settlement dates are not read (the withholding netting key uses the same date as its income). Since #437 this holds for the default too (see "FX trading-date traps"). A trap: cash rows on `settleDate || dateTime` booked a USD fee charged on 31 December, settled 2 January, in the next year (`tests/integration/fx-traditional-cash-dates.test.ts`). Same-day order (`sortEvents`, both methods): acquisitions → stock legs → disposals; among the stock legs, a sale of a position not bought that day or of shares bought on an earlier day (`heldBefore`, even when the position is bought again that day; #437 in the default, #446 here), then each same-day round trip in upload order (its buys, then its sales of shares bought that day), then a buy of a position not sold that day. `tradeTime` is ignored on purpose: a day's trades settle together, and the timed order left phantom dollars when a margin round trip came before the sale that funded it (S3d: +52.50).
- **Late cover (7 days), planned in passes** (`processWithCovers`; every method that runs the FX engine since #437, the default included): pass 1 runs with no cover and records every `null` park. In a cover pass, a covered buy that finds the pool empty takes, oldest first, the part of each acquisition of that currency (conversion, dividend, interest) dated 1 to `LATE_COVER_DAYS = 7` calendar days after it, up to what it lacks, into the pool on the buy's date (own rate, own date as the lot's acquire date; trace: an `acquire` row with a `cobertura tardía` note). So the result equals "funded before the buy" (MG0) even when a sale returned part of the principal before the funding (S5c: −172.50 → −80). Pass 2 also lets lots a sale returns cover `null` slices parked the SAME day (trace: `park` row, `cobertura del mismo día`; S3j), in the order their buys ran across all positions (a trap: walking the parked map in insertion order covered an older position's later buy first and moved FX between years, SDO). Since #446 a sale of held shares runs before every buy of its day, so only a sale of shares bought that same day (an intraday round trip) can still return lots after a `null` park; there the map-order trap moves which position keeps the untracked slice (SDO-INTRADAY), and a cover that hands the dollars back to the round trip and leaves a later buy `null` is dropped (SDR). An intraday round trip with no dollars of its own pays back what its buy borrowed for the day, a loss leaves a debt the day's next returned currency pays first, and in a trial its sale takes the same-day cover as part of the chain (all since #447, see the FX trading-date traps). A buy that spends more dollars than the account holds and is paid by a LATER DAY's inflow (the account stays below zero overnight) is a loan from the broker since #449, but only for a currency whose cash an IBKR CashReport proves (see "Balance below zero = loan from the broker"); everywhere else it keeps this untracked path and can still miss the economic total. Precedence (G2, iterated): the acquisition covers the `null` buy first, even when pass 1 gave it to a later buy; that later buy, now `null`, takes its own acquisitions 1 to 7 days after it when it runs, and so on: events run in date order, so one pass settles a whole chain (a trap: letting the later buy keep the funding gave a monthly buy-then-fund chain −300 on an economic −250, L5; a trap: one pass per link, capped at 25, broke a weekly chain past week 25 and took seconds for 300 buys). A cover must never leave new uncovered principal: no buy may park more `null`, and no currency may get more `fx.missing_prior_lots` (the buy really used an untracked opening balance, S5d / S10b), than without it, over ALL the data (a trap: a 29 Dec buy covered by a 2 Jan conversion was judged only up to 31 Dec, and the next year got +150 and a false missing-lots note, Y6; a trap: judged up to the end of its own years, a December cover left a conversion of the next year without a lot, −30 instead of −80, Z1). A cover's horizon is the year of its buys and of the acquisitions they take. One exception: a single cover that holds up to the end of its horizon and fails only in a later year F stays when dropping it would change the FX figures of a year from its horizon to F − 1, because those years were filed with it; year F then shows its `fx.missing_prior_lots` / `fx_traditional_uncovered` note (Z2: 2023 stays 123/1 instead of 123/31 because of a 2024 conversion). A kept cover takes only its own chain: a later buy it left without dollars keeps them lost and is judged as a cover of its own year. So a filed year never changes because of later data, unless one of its covers takes an acquisition of that later year. Covers are judged per year, oldest first: the whole year at once, then the oldest half, halving after each failure and doubling after each success, down to one cover with its chain. A batch must hold over all the data; a cover only takes dollars away from what comes after it, so each cover of a kept batch holds alone too, and only a single cover gets the exception: batches change no result (the chains test runs them both ways with `FxFifoEngine.coversAlone`; a batch judged only up to its own year kept two failing covers, BATCH-Z1). Only the failing cover is dropped (a trap: dropping every cover of the currency let a 2024 same-day case undo a 2023 late cover, L9). Trials stop at the first certain failure and run without the trace; only the kept pass records it. A `null` slice from a deposit, an older year, or a balance below zero outside the #449 loan gate keeps the untracked path and `report.fx_traditional_uncovered` says so (its text names an overdraft or margin loan among the origins).
- **Messages** (all `report.fx_traditional_*`, Spanish text byte-identical to the `es` locale; titulares-split): `method` (info, always), `risk` (warning, always: V1740-17 for shares; V1615-25 rejected this valuation for a US flat, never cite it as a share ruling; never claim 0588 is unchanged, and never claim equal totals when a sale lost money), `no_conversion`, `lost_dollars` (only real `stock_sale` rows), `guard` (info: negative-cost guard rows, trigger `stock_sale_guard`; the currency came back, so never call them lost), `inflight` (warning, ≥ 1 €: dollars converted this year whose drift a stock sale of an EARLIER year declared, from `FxDisposal.declaredShiftEur`), `uncovered`, `orphan` (warning: principal still parked under a position with no shares at the declared year end — ISIN change, merger, spin-off; computed from an engine checkpoint at the year end against `isin || symbol` of the remaining lots). In the mode they replace `competitor_reconciliation`, `fx_method_consistency` and `fx_deferred_no_conversion`.
- **Limits (documented, tested)**: TC merger / ISIN change and spin-off leave principal under the old key (orphan warning gives the undeclared amount); a scrip dividend lot has no parked principal; a delisting with no sale trade frees nothing; a call exercise parks the strike through the `Ex` STK row but the premium has no FX event; Degiro AutoFX / Trading 212 EUR accounts can book lost-dollar rows from dividend lots that never existed (needs the `brokerConvertedToBase` follow-up of the #96 section). Non-goals: options, shorts, unknown cash types.
- **Never claim** parity with Autodeclaro or TaxDown for currency, that the DGT approves this method for shares, or call it «criterio DGT de fondos».

### FX trading-date traps (Hard Trace — issue #434)
- **Same-day order**: a same-day rotation (sell A, buy B) booked +175 on 400 when the buy ran first: it parked "uncovered" while A's dollars stayed in the pool. Fixed in the mode by the leg order (rank, never trade times) plus the same-day cover. The same-day cover keeps the lifetime total right in either order, but the order still decides WHICH dollars a buy takes (a sale's re-added dollars keep their old date and are FIFO-first), so it moves FX between years — pinned by the ROTF test, which goes red when the order is removed.
- **Same-day rebuy of a held position with late funding (issue #446)**: the mode ran a same-day sale and rebuy of a HELD position as a round trip (rebuy first). The same-day cover settled the plain case, but in the cover pass the rebuy found the pool empty, parked `null` (or took a later conversion as its late cover), and step 4 then judged an earlier late cover as one that leaves new uncovered principal and dropped it; that funding stayed in the pool (HB446: fund-late AAA, then sell and rebuy BBB on one day: −320 on an economic −270). Of 200 random closed cycles (late funding, rotations, rebuys, no forced loss sales) 26 missed. Fixed by the default's held-before rank (`FxEvent.heldBefore`, now set in every method that runs the FX engine, on ordinary sales and on both events of a cross-currency sale: the release in the lot's currency and the proceeds in the sale's currency; a trap: without it on the proceeds, AAA bought in EUR, sold and bought back in USD on one day, ran the USD rebuy first, which parked an earlier late cover's funding and dropped that cover, XEUR-REBUY: −370 on an economic −320): 0 of 200 in both methods, pinned by the seeded property test in `tests/integration/fx-traditional-same-day-rebuy.test.ts` (controls: no held-before on ordinary sales in the mode → 6 tests red; none on the cross-currency release → the XHELD-T mirror goes red). No fixture changed (byte-identical in all 6 option sets). Two review cases now reach their allocation by the order instead of the same-day cover, with the same figures: SDR-HELD (the rebuy takes the old AAA's dollars, the day's last buy BBB parks the untracked 1000; before, BBB took them and the rebuy was untracked) and SDO (held sales return 250, the buys take them in buy order). The same-day-cover tests moved to intraday round trips, the only case that still reaches it. Intraday round trips after a late-covered buy still missed in both methods until #447 (next bullet).
- **Intraday round trip with no dollars of its own (issue #447, both methods that run the FX engine)**: an intraday round trip (a sale of shares bought that same day) whose buy finds the pool short parks the rest `null`: the account went below zero for the day. Two traps. (1) The sale re-added that `null` part at the sale rate, as for an untracked opening balance, so dollars that never existed entered the pool: a conversion spent them before a later-dated late cover, and their transient `null` made step 4 drop an earlier late cover (IRT: AAA bought 03-01 with no dollars and funded 03-04 with 1000 at 0.92, BBB bought 10×100 and sold 10×110 on 04-01 at 0.95, AAA sold 06-03 at 0.85, 1100 converted 09-02 at 0.80: «Tradicional con divisa» −90 on an economic −40; IRT-EARLY, the round trip on 03-02: −120 there and −70 in the default). Fixed: the sale first pays back the `null` slices of its position parked that same day (`borrowedOn`/`repayBorrowed`): those units leave with no FX and no pool lot (trace: `discard` row, note `compraventa del mismo día sin divisa`) and stop counting as `null` for step 4; the proceeds pay back before they re-add older slices, so a loss falls on the held slices (IRT-LOSS: the 800 of a 1000 buy, 500 of them borrowed, pay back 500 and return 300 of the 500 tracked; the 200 lost book their drift in the mode). (2) A round trip whose later buy lost its dollars to an earlier late cover kept them `null` while its own sale returned as many to the pool, because a trial never switched on that day's same-day cover; step 4 then dropped the late cover (IRT-CHAIN: −230 on an economic −180 in the mode). Fixed: `sameDayCoverOn` takes the same-day cover in a trial for a sale whose day has a buy the trial left with more `null` than the accepted pass, as `takeLateCover` does for the late cover (`CoverPass.joinedSame`). An adversarial generator of 1000 closed cycles went from 12 misses to 0 in the mode (without loss sales: from 4 to 0 in both methods), pinned by the seeded property test in `tests/integration/fx-intraday-round-trip.test.ts` (controls over `tests/integration`: `borrowedOn` always false → 13 tests red; no same-day chain → 5 red). (3) A loss round trip's sale cannot pay back all it borrowed, and discarding the rest at once let a later round trip of the same day put its whole profit in the pool, beside the debt it should have paid: the upload order decided the FX (IRT-PAIR-LOSSFIRST, IRT with two round trips on 04-01, CCC 10×100 sold 10×80, then BBB 10×100 sold 10×130: −90 in the mode and −46 in the default on −40, −40 with BBB listed first; RTL-FIRST, the same day with no late cover: 105 on 135). Fixed: what the sale could not pay back is a debt for the rest of the day (`SameDayDebt`, `repayBorrowed`): it stays in the buy's `null` count, and the next currency of that day a sale returns pays it first, oldest buy first, together with the same-day cover (`sameDayCover`, ungated; trace: `discard` row with the paying lot's rate, note `compraventa del mismo día sin divisa`). Paid with currency that cost other than the buy's rate (a round trip covered late), the mode books its drift as a lost-dollar row (DEBT-LATE: 163 × (0.85 − 1.20) = −57.05; without it −228.55 on −285.60); the default books nothing (its loss-sale rule). What is still owed when the day ends is discarded as untracked (`closeDebts`, the default's own note `principal perdido en la venta — sin efecto de divisa`, the mode's `sin origen rastreado`) and counts in the mode's `fx_traditional_uncovered`; the paid-back part does not, because it left the account the day it came. Generator with up to two round trips a day and loss sales: 58 of 2000 missed in the mode, 0 now (seeded test: 9 of 400 → 0; with one round trip a day, 0 before and after). A consequence by design: an intraday round trip changes the pool by its profit only, also when the buy used an untracked opening balance, so a later conversion of that balance finds no lot (zero FX and `fx.missing_prior_lots`), as without the round trip; before, the round trip gave it the sale's rate (IRT-OPEN: −165 → −15). The default's gen2 misses with loss sales (932 of 1000) are its loss-sale zero rule, not this bug: every miss has a sale that loses dollars, and the 65 cycles with none all match. Fixtures: only `degiro-transactions-sample.csv` moved, in its trace and messages, never in a box: its 2021 intraday round trip (770 USD untracked, half sold the same day for 336.86 on a cost of 385) pays back 336.86 and owes 48.14 at the day's end, so it no longer leaves 336.86 USD in the pool for a 2024 buy. The mode's `fx_traditional_uncovered` note goes from 336.86 to 48.14 USD in 2021 and from 105.76 to 442.62 USD in 2024 (the 2024-09-03 buy now finds no lot); the 48.14 row keeps the default's own note.
- **Late funding**: IBKR users often buy first and convert after (or run a short negative balance). Without the 7-day late cover the funding lot never ties to the buy and the cycle is off by `C·(r_s − r_b)` (MG: −120 instead of 80). The default has the same cover since #437 (see its entry below).
- **Settlement vs trade date**: a same-day convert + buy of a US stock settles the stock T+1 and the FX T+2; dated by settlement, the buy parks uncovered and the invariant breaks by `C·(r_s − r_b)` (A9: 25 instead of 225), and two buys settling out of order misallocate years (A2b). Every method that runs the FX engine dates every FX event on its trade date (R0).
- **Lost dollars**: see the per-mode rule above; zero-gain rows are skipped so the trace and the casillas carry no noise.
- **Default mode, phantom dollars (Hard Trace — issue #437)**: dated by settlement, the same A9 pattern left 2000 USD in the default's pool that no longer existed; a later conversion consumed them as real lots (−100 on an economic 0) and `fx.missing_prior_lots` never fired. The default now uses R0 and the same same-day order (`sortEvents`): a conversion is valued at its trade-date ECB rate and belongs to the year it was traded (31 December traded, 2 January settled → the earlier year), the date the stock FIFO uses for a sale. Doctrine: Art. 14.1.c (alteración patrimonial), V2422-20 («tipo de cambio vigente en el momento de la transmisión»), and V0463-21 / V1613-25 read the «cobro o pago» of Art. 14.2.e as «el momento en que dicha conversión se realice efectivamente»; reading it as settlement is possible but splits a stock and its own currency across dates. Real files: on `ibkr-434-cycle-2025.xml` the default's total (stock + FX) went from 169.89 to 183.02 = EUR out − EUR in = «Tradicional con divisa»'s total; on `ibkr-434-afx-2025.xml` from 217.55 to 240.38 = monodivisa's. A same-day rotation (sell A, buy B) used to run the buy first and left A's dollars in the pool too. Trade dating needs the covers that come with it: a trap, R0 alone left the default with no late cover, so a buy funded the next day by a conversion that settled first (a T+0 CASH row, as in the IBKR fixtures) parked `null` and the funding lot stayed in the pool (−220 on an economic −70; settlement dating had hidden it by running the conversion first). The default now runs the same cover planner as «Tradicional con divisa» (`processWithCovers`: the 7-day late cover, the same-day cover, the step-4 refusal when the buy really used dollars the upload never shows). A second trap: a same-day sale and rebuy of a HELD position ran as a round trip (buy first), the rebuy parked `null` and the sale's old principal stayed in the pool (−50 on an economic 200). A sale of shares bought on an earlier day (`FxEvent.heldBefore`) now runs at rank 0, before the rebuy; only a sale of shares bought that same day keeps the buy-first order. Of 200 random closed cycles with late funding, rotations and rebuys (no loss sales), the default matched the economic result in 74 before these two fixes and in all 200 after. «Tradicional con divisa» kept the round-trip order until #446 and missed 26 of them, all where a late cover and a same-day rebuy meet; it now uses the same rank (see "FX trading-date traps"). Pinned by `tests/integration/fx-default-trade-date.test.ts` (controls go red: settlement dating, the old buy-before-sell order, no covers in the default, no held-before rank, held-before on a same-day lot, and a step-4 mutation for the opening-balance case). Why #148 had moved to settlement: the old model consumed currency at the stock BUY, so a buy dated before its funding fired false missing lots; the carry-basis buy only parks.

### Balance below zero = loan from the broker (Hard Trace — issue #449)
- **The bug**: a buy that spends more dollars than the account holds took the missing part as untracked (`null`), as for an opening balance the upload does not show. When a LATER day's inflow paid it (a sale of other shares, a conversion), the sale re-added that part to the pool as if it existed, and a conversion spent dollars that were owed, not held. REPRO (500 USD at 0.90 buy CCC; BBB bought for 1000 with no dollars at 0.95 and sold for 800 that day; CCC sold for 500 next day; 1000 funded at 0.80; 1300 converted at 0.85): −175 in both methods on an economic −145, the pool ending with 200 dollars the account never had. HELD / YEAR (the loan repaid by another sale and a later funding, YEAR across 31 December): 43 in «Tradicional con divisa» on 143. Of the issue's 200 generator seeds, 151 missed in the mode and 129 in the default.
- **Why a gate**: from the trades alone, a loan looks the same as currency from outside the upload (an opening balance, a deposit, AFx rows skipped under the #239 opt-out, DEGIRO AutoFX). An ungated loan model broke 47 existing tests and booked results that never happened (an AFx-skip round trip went from 40 to 90 in the mode). So `loanCurrencies` (`src/engine/fx-loan-gate.ts`) turns the model on per currency only when the upload proves its cash, failing closed on anything it cannot prove: CashReport rows of that currency (the parser now keeps `startingCash`, `fromDate`, `toDate`, the row's dates or else its statement's) for one account and one broker, each with a non-blank `accountId`, real calendar dates with `fromDate` ≤ `toDate` after `normalizeDate` (which reshapes "20250001" without checking it), and an `endingCash` the broker wrote (the parser still gives Modelo 720 "0" for a missing one and flags it `endingCashMissing`), first `startingCash` known and ≥ 0, periods chained without overlap (each starts within 1 unit of the previous ending), every event of the currency inside a period and from that broker, each period's `startingCash + Σ flows = endingCash` within `CASH_TOLERANCE = 1` (flows: conversions, income, fees, interest, stock buys −cost, stock sales +proceeds), and no AFx row of the currency skipped. **And every raw row that moves the currency is one the engine reads, of that account and broker** (`rowsReadable`): CASH pairs and STK/FUND/BOND trades only (no OPT/FUT, no short cover — a short sale's unseen inflow breaks the reconciliation —, no commission in the currency on a trade in another one), cash rows of income, withholding, interest or fees only (no Deposits/Withdrawals, transfers or other types), no corporate action with cash, no opening short sale (`SELL` with `openCloseIndicator` "O": the stock FIFO opens a short lot and makes no disposal); and no cash row of the currency is one `extractCashFxEvents` drops (an orphan withholding, the part of a withholding its income does not absorb, a row with no ECB rate on its date or the 9 days before, a net refund or reversal it cannot emit: it lists them in its optional `omitted` argument, `report.ts` passes them as `omittedCash`), and each DAY's cash rows add up exactly to the cash events of that day (`cashRowsSeen`; a withholding netted into its income that day still adds up). A trap, PR #460 review: compared per period, a credit with no ECB rate and an equal orphan withholding on another day both vanished and the period added up. Two traps the per-period net hid (review of the lane): a USD deposit and an equal withdrawal in one year reconcile while the balance never went below zero (an invented loan, 70 € in the mode); account U2 with no CashReport merged with U1's CashReport passed because the event check compared only the broker (70 € / 30 € of phantom repayments). The gate reads the stock sales with the mode's producer (`extractStockProceedsFxEvents(..., { traditionalFx: true })`, every sale also at proceeds ≤ 0) in both methods: a trap, a worthless sale whose commission exceeded its proceeds counted in the mode's reconciliation only, so the same upload ran the loan in one method and not the other. `report.ts` reads the rows from `holdingsBySource` (every statement, also those `yearEndHoldings` drops from Modelo 720); duplicate rows (the same file twice) count once, keyed with the broker. Traps of the PR #456 review: "2025-00-01" .. "2025-99-31" held every date of 2025; blank account ids matched each other; a missing `endingCash` read as "0" reconciled REPRO (its dollars end at 0); the same row stamped by two brokers deduplicated to one before the one-broker check; an opening short sale's +100 and an orphan withholding's −100 cancelled in the period.
- **The model** (`FxFifoEngine({ loan })`, both methods; monodivisa unchanged): the opening balance (`startingCash`) is spent first, as untracked, before any pool lot: it was in the account before the first period, so it is the oldest currency (a trap, PR #456 review: spending a newer tracked lot first booked its gain in the wrong year, 100 in 2025 instead of 0 / 50; `consumeLots` books it with the untracked row, `parkPrincipal` parks it `null` first in the position); then the pool lots; then the 7-day late cover; what still lacks is borrowed: a parked slice at the buy's ECB rate (`borrowForBuy`, trace `park` note `préstamo en divisa`) and a `SameDayDebt` with `loanSince`. A debit (fee, interest) with no lots borrows too (`borrowForDebit`: a `dispose` with `lotId: "LOAN"`, gain 0 only when no commission is allocated to it; an allocated commission lowers the proceeds and not the cost, so it is a loss of that commission, as `docs/traza-fx.md` says), so debit interest charged while the balance is negative adds to the debt. The opening balance is not used while a loan is open. Every later inflow repays the open loans FIFO (`addLot` → `repayLoans`; a sale's returned lots via `sameDayCover`), booking `x·(r_loan − cost)` as an `FxDisposal` with `trigger: "loan_repayment"` and `loanDebtPartEur = x·(r_loan − r_day)` (the debt's own change), in «Tradicional con divisa» with the paying lot's shifted cost. A late-cover part never repays a loan: it pays its own buy. `closeDebts` keeps open loans across days. The planner keeps working because a loan's `NullPark` keeps its gross qty. In the default, a sale with proceeds ≤ 0 in a loan currency reaches the engine too (`report.ts` takes the gate's sales for it; the producers differ only in that filter): its principal is discarded with no FX (the loss-sale rule) and the commission above the gross consumes like a fee (a trap: the 5 USD of a worthless sale's commission stayed in the default's pool while the gate counted them).
- **Same-day trap**: a loan opened and repaid by the same intraday round trip must keep the #447 rule: the sale first pays the loan back with its own dollars, no FX, no pool lot (`borrowedOn` true for a loan slice on its `loanSince`; `repayLoanSameDay`), and a loss leaves the loan open. A trap: re-adding those dollars at the buy's rate and repaying with the oldest pool lot moved IRT-LOSS in the default to −190 / −45 (against −190 / −30; mutation-checked). The default books nothing for a loan repaid the day it opened: borrowed currency still parked in the shares takes the paying lot's cost and date instead (`coverLoanSlices`, trace `park` note `…paga la compra en lugar del préstamo`), as the #447 same-day cover does for `null` slices, and borrowed principal a losing sale did not return follows its loss-sale rule. A trap (review MIN1: 500 USD at 0.90, buy 1000 at 0.95, sell half for 510 the same day, the rest later): discarding the repayment and leaving the borrowed slice parked at 0.95 lost 500 × (0.95 − 0.90) = 25, −27 on an economic −2 (f9926b6 and the upload without a CashReport give −2); 47 of 1500 no-loss generator seeds with same-day sales missed. Only debts that survive the day book there. A same-day payback repays only what the loan still owes (`splitRepaidLoan`, `borrowedIn` with the live `qty`): the part an earlier inflow of the day repaid is principal again and re-adds like a covered slice (a trap, review: in «Tradicional con divisa» the first of two same-day sales repaid the loan with its tracked dollars, the slice kept its loan mark, the second sale paid it again, took the debt below zero and discarded 500 USD as lost; with the same rate the totals hid it, the trace did not). Opening balance a same-day sale returns repays that day's open loans before it goes back to the opening balance (`repayLoansWithOpening`: the loan's slices become untracked opening slices; a trap: 500 of opening, a buy of 1000 and a sale of 400 that day left 500 owed instead of 100, and a later 500 inflow repaid 500). Opening balance a same-day loss sale does not return is lost principal at once (`repayBorrowed` → `discardUntracked`, the row `closeDebts` writes, counted in `fx_traditional_opening`), never a #447 same-day debt: in a loan currency every `null` slice is opening balance the account really held (a trap, review: D2, 500 of opening, AAA bought for 500 and sold for 300, then CCC bought for 100 and sold for 400 that day: the 200 lost became a debt, CCC's profit paid it, 200 real dollars left the pool and the final conversion opened a loan nothing repaid, 80 on a true 50 in both methods; Z1, AAA sold for 0, 160 on 145; already on #456 in 63 of 300 seeds of the reviewer's generator).
- **Law**: STS 71/2021 (ECLI:ES:TS:2021:345) puts the exchange difference on repaying a foreign-currency loan in the base general (0304/0305); DGT V2414-12 puts it in the base del ahorro. DeclaRenta books the whole repayment in 1633/1637 and `report.fx_loan_repayment` (info, both methods, 5 locales, a method note in the open «Cómo se ha calculado» box) gives the debt part for the user who follows the Supreme Court: Σ `x·(r_loan − r_day)` over **every** repayment of the year (`getLoanRepayments`, also the gain-0 `discard` rows), gains and losses apart (`gain` → 0304, `loss` → 0305, both positive), and the hint says to take them out of 1633/1637 (lower 1633 by the gain, raise it by the loss). That instruction holds only for the part a `loan_repayment` row in 1633/1637 holds (`LoanRepayment.inBoxes`; each row's `loanDebtPartEur` is now its own quantity's, not the whole repayment's). When part of it is elsewhere (the default repaying with the shares' own currency at the loan's rate: the change is in the stock line, a gain-0 `discard`; or a same-day cover), the note is `report.fx_loan_repayment_manual`: it gives the part in 1633/1637 (`boxGain`, `boxLoss`) and asks to reconcile the rest by hand (a trap, review: the hint told the user to lower 1633 by 50 € when 1633 was 0). A gain-0 repayment row counts as in 1633/1637 (its debt part and the paying currency's part cancel inside the boxes) unless, in the default, the paying lot is borrowed principal that the shares' sale re-added at the loan's rate (`loanPrincipal`, a map from the lot to the loan of the `loanOfSlice` slice it came from, set in `unparkAndReadd`) and that principal is still borrowed: all of it when it repays its own loan; for another loan, up to its loan's `SameDayDebt.borrowedLeft`, taken first. `borrowedLeft` starts at the loan's quantity and drops when currency in 1633/1637 repays the loan (a row in the boxes, also a gain-0 one), when a slice stops being the loan's on its day (`repayLoanSameDay`, `coverLoanSlices`, `openingForLoanSlices`), and when its principal repays a debt as borrowed currency, with or without a result (borrowed units first); the rest of another loan's principal pays like any lot. Only a gain-0 row counts the borrowed units it spends outside the boxes: a repayment with a result is a row in 1633/1637 whatever pays it. A trap, PR #463 review (PASS: AAA on L1 at 0.95, BBB on L2 of 1000 at 0.94; half of BBB sold at 0.90 repays L1 with L2's principal, 5 €; a funding of 500 at 0.92 repays half of L2; CCC on L3 at 0.94 sold at 0.90 repays the rest of L2 outside; the rest of BBB repays L3): only a gain-0 row took the spent units out of `borrowedLeft`, so L2 still counted 500 borrowed after the funding and the last row went outside too, `boxGain` 35 instead of 55 of 75. Two traps, PR #460 reviews: AAA bought on L1 at 0.95, L1 repaid by a funding at 0.93, BBB bought on L2 at 0.95, AAA's sale at 0.90 repays L2 with L1's principal: a set of tagged lots sent L2's 50 € to `_manual` with `boxGain` 20, the plain note with gain 70 is right (OTHER; seed 180 of the generator's same-day and `twice` modes hit it too, two loans opened at 1.20); then matching the tag to the loan alone gave CROSS (BBB sold first: L2's principal repays L1, then AAA's repays L2, no currency ever paid for either) the plain note, lower 1633 (0) by 100 €, while OWN (AAA first) said `_manual` on the same figures. A principal repaid later by a funding after it already paid another loan as borrowed stays counted outside: the `_manual` note, which fails safe. A trap, review: counting every gain-0 row as outside sent SAME (shares bought with dollars funded at 0.95 on the loan's day repay the 0.95 loan) to `_manual`, while DIFF (funded at 0.94) got the plain note, and lowering 1633 by 50 was right in both; the mirror in «Tradicional con divisa» (a shifted cost 1.00 + 0.90 − 0.95 equal to the loan's rate) did the same. A trap: summing only the rows in 1633/1637 gave no note in the default when the loan's own shares repaid it (the default's sale-rate stock line holds that change), 0 against the mode's 50 on the same loan. ### FX Engine Simplification (Hard Trace — v0.39.2)
- `detectAutoConvert()` was REMOVED — it produced false positives on hybrid accounts (mix of manual + AFx trades), causing ALL operations to disappear
- **Root cause**: A binary global flag can't represent accounts that mix manual conversions and auto-convert. One AFx trade anywhere → entire account classified as auto-convert → all manual CASH trades skipped
- **Approach**: per-trade only, no global flag. `isFxconv()` classifies FXCONV/AFx-marked trades individually; manual CASH trades always generate FX events regardless of what other trades exist. (Per #239, AFx is PROCESSED by default and the `isFxconv()` skip is now opt-out — see the #239 bullet below; this section's point is only that there is no GLOBAL classifier.)
- Securities trades (STK, OPT, etc.) NEVER generate implicit FX events — this matches competitor behavior and avoids phantom gains from missing prior-year lots
- `extractCashFxEvents()` always processes dividends/interest (no `autoConvert` param) — FCY income creates acquisition lots

### IBKR auto-convert (AFx) processed by default; skip is opt-out (Hard Trace — #239)
- **Symptom**: silently SKIPPING FXCONV/AFx conversions dropped REAL divisa gains. IBKR does NOT round-trip FCY→EUR when you sell a stock — the taxpayer genuinely holds the foreign currency, and its later auto-conversion is a taxable divisa gain. Proof: fund $10000@0.90 then auto-convert @1.00 gave **€0** instead of the correct **€1000**.
- **Fix**: the engine now PROCESSES auto-conversions by DEFAULT (`ReportOptions.trackAutoConvert`, default `true`). `isFxconv()` is RETAINED — it is the per-trade detector that the OPT-OUT uses to restore the old skip for accounts that genuinely round-trip: `trackAutoConvert=false` / CLI `--skip-auto-convert` / web profile checkbox. The missing-prior-year-lot floor (`costBasisEur = proceedsEur` → gain 0) still applies, so processing an AFx conversion can never fabricate a phantom gain.
- **Legal basis**: divisa is a patrimonial element (**Art. 33.1**), timing = the conversion (**Art. 14.2.e**, "se imputará en el momento del cobro o del pago"); **DGT V2422-20** — a held FCY's conversion is a gain regardless of how the currency was acquired ("cuando lo recibido sean divisas… se imputará en el momento del cobro o pago"). There is NO de-minimis, so even tiny sweeps are processed.
- **Not a phantom re-arm**: this is purely the PER-TRADE default; the GLOBAL `detectAutoConvert()` flag stays removed (#171). The carry-basis model means a stock BUY emits no disposal, so nothing re-arms the missing-prior-year-lots phantom-gain bug.
- **Posture**: rigorous-by-default + opt-out checkbox, consistent with monodivisa.

### FX dividend/interest withholding = pago a cuenta, NOT a disposal (Hard Trace — issue #225)
- **Symptom**: a FCY dividend with withholding created a GROSS acquisition lot AND a separate WITHHOLDING disposal that FIFO-consumed the OLDEST FCY lot (often a prior conversion at a different rate), fabricating a phantom Art. 33 FX gain into casillas 1633/1637 on currency the taxpayer never converted to EUR.
- **Why wrong**: withholding (retención en origen) is a **pago a cuenta** — deducted at source, the withheld FCY never enters the taxpayer's spendable balance, and it is **not a conversión a euros**. The DGT FX-timing doctrine (V2422-20, V1613-25, V0463-21) crystallizes an FX gain ONLY on the effective conversion to euros (cobro/pago, Art. 14.2.e). No tool we know of books an FX gain on withholding (IBKR's Forex worksheet covers only completed conversions). No binding consulta is squarely on point — this is a reasoned, conservative position (removes a phantom disposal of money never received).
- **Fix** (`extractCashFxEvents`): a pre-pass sums withholding per `(broker, currency, date)`; each `Dividends`/`Payment In Lieu`/`Interest Received` inflow is emitted as a lot for the **NET** (gross − matched withholding) FCY actually received; the `Withholding Tax` row emits **no disposal**. FX lots are fungible per currency, so (broker,currency,date) netting equals exact issuer pairing; the broker in the key keeps a withholding out of another broker's same-day lot, so the FX rows' buy-broker label stays right. Guards: withholdings net **with their sign** (issue #436, below); an **orphan** withholding (no same-key income — cross-date reclaim) is dropped, never a disposal; interest withholding nets too.
- **Income path is untouched**: gross dividend → 0029 and withholding → 0588 are computed in `dividends.ts`/`double-taxation.ts` from the raw cashTransactions, never from FX events. Only 1633/1637 (and marginally `totalSavingsBase`'s positive-FX term) change.
- **Corrections net with their sign (issue #436)**: IBKR corrects a withholding with three rows on the dividend's own dateTime/settleDate (original −, reversal +, corrected −). The pre-pass sums withholdings SIGNED per `(broker, currency, date)` and no withholding row opens its own lot, so 10 − 1.50 + 1.50 − 1.00 is ONE 9.00 lot (it was 7.50 + 1.50, splitting later FX rows). A net refund joins the first inflow on its key, or, with no inflow (a correction posted in a later file), opens one lot after the loop. Pinned in `tests/engine/fx-fifo.test.ts` and `tests/integration/withholding-correction-e2e.test.ts`.
- **Income reversals keep their sign (Hard Trace — issue #439)**: a dividend reversed and credited again (+10 / −10 / +10 USD) opened three positive lots (20 phantom USD), because the FX path read the RAW cash rows and took `amount.abs()` of every dividend row. The income path (0029/0588) was right: it reads the rows after `collapseCorrections`. Now `report.ts` passes the same collapsed rows (`allCashTransactions`) to `extractCashFxEvents`, in every method that runs the FX engine, and an income row that stays negative (Dividends, PIL, Broker/Bond Interest Received; a reversal on another day or of another amount) nets with its sign into the same `(broker, currency, date)` income AFTER that income's withholding, like #436 (a trap: netting the reversal first let a reversal larger than the day's other income empty it; the withholding then found nothing, was dropped as an orphan, and 0.75 phantom USD stayed in the pool); what no income absorbs leaves the pool like a fee (a disposal with trigger `dividend`/`interest`, missing-lots floor if none). Mirror: a positive Interest Paid row (a refund) brings currency in, as fees already did. Collapsing also drops a same-day fee charged and reversed (it booked a phantom FX row on the oldest lot). The correction key carries the broker and `brokerConvertedToBase` (a trap: a genuine +10 USD dividend at one broker and a −10 USD reversal of a broker-converted dividend at another, same ISIN and date, cancelled each other, so the genuine 10 USD vanished from the FX pool). No fixture changed. Pinned by `tests/integration/fx-dividend-reversal.test.ts` (controls: raw rows → the fee test goes red; `abs()` back → the later-day reversal tests go red). The interest totals keep each row's direction too (PR #444 review): `valueIncomeEur` returns an absolute EUR value and the caller added it unsigned, so a negative Interest Received row raised 0027 and a positive Interest Paid row (a refund) raised the paid total; the broker scope of the correction key made it bite (+10 at one broker, −10 at another, same day: 18 EUR on 0). Now a receipt adds to `interestEarned`, a charge to `interestPaid`, a negative received row lowers the earned and a positive paid row lowers the paid, and each entry's `amountEur` carries that sign. No fixture has such a row. Pinned in `tests/generators/report.test.ts` ("interest totals keep each row's direction").
- **Citation correction**: the FX engine tracks divisa under **Art. 33.1** (transmisión − adquisición), NOT Art. 37.1.l (which is "incorporaciones que no derivan de transmisión" — unrelated). Header comment + this section corrected. This closes the Art.37.1.l→Art.33/V2466-08 follow-up deferred in #220.

### Withholding in another currency than its dividend; broker-converted income opens no FX lot (Hard Trace — issue #96)
- **Symptom**: every Trade Republic foreign dividend lost its Casilla 0588 credit, silently, in default and monodivisa mode. TR keeps the dividend in USD (`original_amount`/`original_currency`) but books the US withholding in the account currency (EUR). `dividends.ts` matched a withholding only by ISIN + **same currency**, so the pair never matched: 0029 stayed gross and 0588 came out 0.
- **Fix (`calculateDividends`)**: pass 1 is the original matcher (same ISIN, same currency, ≤7 days, first unconsumed by index), so every broker that already matched pairs exactly as before. Pass 2 runs after it: a dividend still unpaired takes the first unconsumed withholding of the same ISIN in **another** currency (never for an empty ISIN). Being a second pass, it can only take a withholding no same-currency dividend claimed. The withholding is valued in **its own currency**: EUR → 1:1, a foreign one → its rate on its own date. Never multiply an EUR withholding by the dividend's USD rate. 0029 is unchanged: gross FCY × ECB rate of the payment date (DGT V1024-11).
- **Broker-converted income must not open an FX lot**: TR converts the dividend before crediting it, so the taxpayer never holds the USD. The parser sets `CashTransaction.brokerConvertedToBase` on a dividend whose original currency differs from the account currency, and `extractCashFxEvents` skips flagged rows. Without the flag the TR dollars sat in the USD pool forever: harmless alone, but merged with an IBKR file FIFO consumed them first and shifted 1633/1637 (test: −10.00 alone, −10.38 merged). `trackAutoConvert=false` does not cover this; it filters IBKR CASH trades only.
- **Same class, not yet flagged**: Degiro AutoFX (keeps FCY dividends, drops the AutoFX rows) and Trading 212 EUR accounts (trades in the price currency). Set the flag in those parsers when they are fixed.
- **Pinned by**: `tests/engine/dividends.test.ts` ("withholding in another currency (issue #96)"), `tests/parsers/trade-republic.test.ts` ("foreign dividends credited in EUR") and `tests/integration/tr-foreign-dividend-e2e.test.ts` (0588 = 2.63, empty TR FX trace, TR + IBKR merged = IBKR alone).

### A dividend's withholding is the signed sum of all its rows (Hard Trace — issue #438)
- **Symptom**: 0588 too high when a broker corrects a withholding with anything other than an exact same-day reversal. A partial refund (−1.50, then +0.50) or a reversal and a new withholding on another date (−1.50 / +1.50 / −1.00) gave 1.50 USD of tax instead of 1.00. `calculateDividends` paired each dividend with ONE row and took its `.abs()`; `collapseCorrections` cancels only exact same-date, same-amount pairs, so every other correction row was dropped, and a refund listed first could even become the pair (its absolute value counted as tax).
- **Fix (`dividends.ts`, `matchWithholdings`)**: passes 1 and 2 are the old matchers (same currency, then the #96 cross-currency fallback), but a positive row (refund or reversal) is never a pair, and a negative dividend (a reversal) never takes a withholding. Pass 3a gives every negative row still unpaired to the nearest dividend of its ISIN within ±7 days whose pair is in the row's currency (a dividend with no pair has none in reach: passes 1-2 took it). Pass 3b gives each refund to such a dividend, but never more than that dividend still has withheld (its capacity): first a dividend with a withholding of exactly the refunded amount, then one that withheld at least the refund, then any with capacity, nearest date, then file order; the rest goes on to the next one. When every dividend in a refund's reach is full, an earlier refund that has another dividend in its own reach moves there to make room (an augmenting path, shortest first), so a refund is left out only when no allocation of all refunds could fit it. Rows with no ISIN also need the same symbol, in pass 1 too (pass 2 never runs for them), and `collapseCorrections` keys them by symbol too, so a refund of BBB never cancels a withholding of AAA before the matcher runs. A row posted in a later year than its date (IBKR `reportDate`) joins only a dividend of its own year, in every pass. The withholding is `−Σ part × rate` over the dividend's parts, each row at the dividend's rate when it is in the dividend's currency, else at its own rate on its own date; a net refund counts as 0. Each row's parts add up to at most the row, so nothing counts twice. Art. 80 cap and treaty limits (`double-taxation.ts`) are untouched. Byte-identical on all committed fixtures in the three FX methods (one row per dividend there).
- **Traps the first version fell into**: (1) the refund went to the nearest dividend and the per-dividend clamp at 0 threw away what it took beyond that dividend's own withholding (a PIL of 0.30 next to a dividend of 1.50 lost its 0.30; a 0.50 refund next to a 0.20 withholding lost 0.30), so 0588 stayed too high. (2) A reversed dividend (−10.00) anchored the rebook's −1.00, so the +1.50 reversal had nowhere to go. (3) A weekly payer's correction posted in January but dated on the 27 December dividend is exactly 7 days from the 3 January dividend: it lowered the new year's 0588 AND fired the warning, so the user would lower both years. (4) In a merged upload a refund or extra withholding at one broker joined another broker's nearer dividend of the same ISIN (broker A's 31 December dividend kept its 15 withheld and broker B's 2 January one netted 0); pass 3 now takes only a dividend of the row's own broker (a row with no broker name, as in a single-broker file, joins any), pinned by "withholding corrections stay at their own broker". Passes 1 and 2 pair only within one broker too (`findWithholding` applies the same `sameBroker` test, with the same fallback for a row or dividend with no broker name): a trap, with A's dividend listed first and B's −5 before A's −15, pass 1 made B's −5 A's pair, so A's +15 refund found only 5 to take back and dropped 10 (15 on an economic 5); the same for pass 2's cross-currency pair. Pinned by the same describe. No fixture moved (one broker per file).
- **Prior-year warning (`report.withholding_corrected_prior_year` for 0588, `report.spanish_withholding_corrected_prior_year` for 0597, warning, 5 locales)**: computed by `priorYearWithholdingRefunds` in `report.ts` with the same matcher. Each of its two runs matches the rows the report matches: `collapseCorrections` on that run's rows, so a dividend reversed on its own day never takes a withholding the report gives to the rebooked dividend (a trap: the raw rows let the reversed 3 March dividend take a 3 March withholding the report gives to the 10 March rebook, so a later refund was stated at 3 March's rate). A dividend the collapse cancels stays in the run with no withholding (`matchWithholdings(rows, cancelledDividends)`): a filed dividend reversed by a row posted in the report year is still found, and its whole filed withholding is the drop; dropping it from the run would lose it. This year's rows are the rows posted in the report year (`reportDate` when present, else the row's date). For each dividend posted before the report year (filed), the drop is its withholding as filed (the matcher on the rows posted before the report year) minus its withholding with this year's rows too (the rows posted up to the report year), both valued by `withholdingEur` (the same valuation as `calculateDividends`), so the stated drop is what the recalculated year loses. A trap: summing only this year's parts missed a filed refund that a late refund pushes to another dividend (`makeRoom`): it leaves its own dividend, so a 0.90 € drop was stated as 0.80 €, and when it lands on a dividend posted in the report year it lowers that year's own boxes AND was also counted in the warning. A part of this year's row that joins no dividend counts at its own date's rate for the year it is dated in (IBKR, earlier file not uploaded), or for year − 1 when dated 1-7 January. A part that joins a dividend posted in the report year is that dividend's own withholding, never filed, so it never offsets a refund. Each year and box gets its own message: a Spanish withholding (`withholdingCountry` = ES, the dividend's country or, unjoined, the row's own) went to casilla 0597, so it warns with `report.spanish_withholding_corrected_prior_year`; any other country warns about 0588. Years whose net lowers the withholding warn (amount titulares-split). A late correction that RAISES the withholding gets no message. The report year's own boxes never include the correction.
- **Limits**: a refund dated more than 7 days from every dividend it could correct is left out (as before). When the dividend it corrects is not in the data, only an IBKR late row (dated in the earlier year) or a refund dated 1-7 January is reported; another orphan refund is dropped silently. Two dividends of one ISIN in one window can still share a refund between them in another proportion than the broker meant; the total per ISIN stays right while every candidate is in the same year. When the broker re-posts the DIVIDEND rows themselves next year (−10 / +10), the warning can overstate the refund.

### FX from foreign-currency stock round-trips = carry-basis defer (issue #230 → follow-up; supersedes the full-proceeds model)
- **What it does**: a foreign-currency stock BUY now SILENTLY CONSUMES the FCY it spends from the FX pool and PARKS the carried EUR basis of those dollars; a foreign-currency stock SELL pulls that principal back into the spendable pool at its CARRIED (original-acquisition) basis plus the trading profit at the sale-date rate. Neither emits an `FxDisposal` (deferred per Art. 14.2.e LIRPF, unchanged). An FX gain or loss comes only from currency that leaves the account through `consumeLots`: a real conversion (FCY→EUR, or the given-up side of an FCY→FCY pair), a fee or commission paid in the currency, interest paid in it, or an income reversal no income absorbs (#439). The one stock-sale exception is a sale in another currency than its lot (`stock_sale_cross`, #441 bullet below). Wired in `report.ts` inside the `skipFx` block alongside CASH conversions (`extractFxEvents`) and dividend/interest inflows (`extractCashFxEvents`); the stock-event producer lives in `fx-fifo.ts` and is fed both the BUY and SELL legs from `fifo.ts` (`getDisposals` plus the buy ledger), not the sell-only `extractStockProceedsFxEvents` of the old model.
- **Hard-Trace symptom that killed the previous (full-proceeds) model — the €450-vs-€320 drift**: the v0.49.0 model pushed each SALE's full net `proceedsFcy` into the FX FIFO as a pure acquisition lot and did NO buy-side accounting. Because a stock BUY never removed the FCY it spent, the FX FIFO balance DIVERGED from the real spendable balance across multiple same-currency round-trips, and a later conversion consumed the WRONG "oldest" dollars. Numerical proof on a two-round-trip account: the engine reported **€450** of FX gain where the correct figure is **€320** — off by **€130**. The old section's claim that the no-buy-side model "matches the V2324-10 symmetric criterion" and that "over-accumulated sell-proceeds lots sit unconsumed at the tail and are never taxed" was therefore PROVEN FALSE: those orphan lots do not sit harmlessly at the tail, they shift the FIFO frontier and mis-rate a real conversion. That model is gone.
- **Parked-FIFO mechanism (the fix)**: per currency the engine keeps the normal spendable FIFO PLUS a "parked" FIFO holding the principal locked inside open foreign-stock positions. A **BUY** removes `costBasisFcy` worth of dollars from the spendable pool and parks them carrying their EUR acquisition basis (no disposal, no realized gain). A **SELL** removes the matching principal from the parked FIFO and re-adds it to the spendable pool at its CARRIED basis, then adds the profit (`proceeds − cost`, when positive) at the sale-date rate as fresh dollars. The buy↔sale FX drift on the principal is thus deferred inside the carried basis until a conversion realizes it, instead of being lost (old decoupled engine) or double-injected (old full-proceeds engine). On the €320 two-round-trip case the carry-basis engine now reports exactly **€320**.
- **Same-day ordering in `processEvents`** (`sortEvents`, every method that runs the FX engine, on trade dates — R0, #437): events on the same date are processed pool-acquisitions → stock legs → disposals (conversions); among the stock legs a sale of a position not bought that day runs first (also a sale of shares bought on an earlier day, `heldBefore`: #437 for the default, #446 for «Tradicional con divisa»), then each same-day round trip (its buy parks its dollars BEFORE its sale re-adds them), then a buy of a position not sold that day. So a buy parks BEFORE a same-day conversion can consume the dollars, and a rotation's buy takes the dollars the sale returned. With no stock events present this collapses to the prior acquisitions-before-disposals order.
- **Funding-absent no-op = the dominant-case safety property (BYTE-IDENTICAL to the old behavior)**: when the FCY a buy spends has NO tracked acquisition lot in the data — the common real-file case: IBKR auto-convert (AFx) settlement, single-year Flex exports, or (under the #239 opt-out) FXCONV-skipped conversions — the buy parks "uncovered" (nothing to remove from an empty pool) and the matching sell re-adds at the SALE rate, which reproduces the previous full-proceeds result exactly. One exception since #447: a sale of shares bought that same day pays the `null` part back instead (see "Intraday round trip with no dollars of its own"). Another since #449: in a currency whose cash an IBKR CashReport proves, only the shortfall left after the available cash (the CashReport's opening balance, which still parks `null`, and the pool) and an accepted late cover is a loan from the broker (see "Balance below zero = loan from the broker"); no fixture passes that gate, so every fixture stays byte-identical. So nothing changes for the overwhelming majority of files; the carry-basis correction only bites on accounts that hold TRACKED FCY across multiple same-currency stock round-trips AND then convert to EUR.
- **Shares bought in one currency, sold in another (DEFAULT method, Hard Trace — issue #441)**: the default's stock line for such a disposal is already `P·r_s − C·r_b` (`disposalEur`: a lot in another currency than the sale keeps its own buy-date rate, because the gain has no single currency and V2422-20's "compute it in the currency, convert the difference" cannot apply). So the dollars left the account inside the shares at `r_b` and never come back as dollars: the sale releases the position's parked principal and books each covered slice's drift `x·(r_b − r_lot)` as an `FxDisposal` with `trigger: "stock_sale_cross"`, dated on the sale (the moment the default learns the dollars will not come back; deferral as for a conversion, V0152-26), gain or loss alike: the loss-sell zero rule below does NOT apply, because nothing is discarded at the sale rate and the stock line already took the dollars at `r_b`. The sale's own currency, if foreign, enters its pool whole at the sale rate, never unparking another lot's principal of the same ISIN. Same code path as «Tradicional con divisa» (`releaseCrossCurrency`; the default uses the disposal's `acquireEcbRate`, the rate of the stock line's cost, the mode each slice's `buyRate`) and `FifoEngine({ markLotCurrency: true })` whenever the FX engine runs (monodivisa keeps its disposals' shape; crypto permuta disposals in the default now carry `acquireCurrency` too, metadata only). Traps fixed: fund 1000 USD for 800, buy at 0.90, sell for 1000 EUR gave 100 on an economic 200 (now 100 + 100); a GBP sale gave 20 on 120 (now 60 + 60); a EUR lot sold in USD unparked another lot's USD, −65 on −60 (now −60). The release carries `heldBefore` like an ordinary sale of shares bought on an earlier day, so it keeps the stock FIFO's sale order (a trap: ranked as a round trip, sell lot 1 for EUR, sell lot 2 for USD and buy back in USD on one day ran the USD sale and the rebuy first; the release then took lot 2's slice, 200 on an economic 100, and the rebuy carried lot 1's rate). Pinned by `tests/integration/fx-default-cross-currency.test.ts` (controls: no `markLotCurrency` in the default, no cross rows).
- **Loss-sell carried-principal (DEFAULT method, a sale in the lot's own currency; «Tradicional con divisa» books lost-dollar rows instead, see its section): un-converted dollars correctly produce ZERO in the casillas (NOT a residual that ever reaches a declared box — confirmed with issue #230's reporter)**: any same-currency SELL that realizes a LOSS discards the carried principal it pulls back from the parked FIFO (the leg re-adds principal at its CARRIED basis only up to `min(cost, proceeds)`; the rest is drained from the parked queue and pushed to NO pool lot). A same-currency loss-sell emits **no `FxDisposal`** and books **nothing** into casillas 1633/1637: a disposal comes only from currency that leaves the account (a real conversion, a fee or commission or interest paid in the currency, or an income reversal no income absorbs, all through `consumeLots`) or, the one stock-sale exception, from a sale in another currency than its lot (`trigger: "stock_sale_cross"`, the #441 bullet above), which books its drift for a loss too because the stock line already took those dollars at `r_b`. The casillas sum the year's disposals (`report.ts`: `fxDisposals` filtered by `disposeDate`). This is **fiscally correct and is exactly the reporter's principle** (issue #230, 2026-06-17): the dollars spent inside a losing position never reached a EUR conversión, so under **Art. 14.2.e** ("se imputará en el momento del cobro o del pago") there is no divisa gain/loss to compute — *"como si te hubieras comprado una hamburguesa en dólares"*. The €-loss lands entirely in the stock line at the sale-date rate (V2422-20). Pinned by `tests/integration/fx-carry-basis-e2e.test.ts` ("FCY stock loss-sell with NO EUR conversion → divisa 1633/1637 = 0").
- **The so-called "residual" is a gap-vs-raw-economic, never a casilla error**: `residual = Σ over loss-sells of [ discardedPrincipalQty × (saleRate − carriedBasisRate) ]` is the difference between the engine's (correct) casilla figure and a *raw-economic reconciliation* — a benchmark the engine deliberately does NOT compute, because forcing it would **DOUBLE-COUNT** the FX drift against the already-recognized stock loss. That gap is unbounded in magnitude and rate-path-dependent in sign (under-states the raw-economic FX when the rate rose between buy and sale, over-states when it fell), but it lives only in the V2422-20 "two-element" seam — it **never lands in 1633/1637**. The discard is also *clean*: it mutates only the per-position parked FIFO, never the spendable pool, so it cannot shift the FIFO frontier for a later conversion. The earlier framing of this as an "unbounded residual / NOT a bug" was anxious about the wrong benchmark; the casilla output is simply the only-real-conversions figure, which is the right one.
- **Re-added principal keeps its ORIGINAL acquisition date for FIFO ordering (issue #230, comment 4729376344 — wrong-YEAR attribution fix)**: the spendable pool is consumed oldest-first BY ARRAY POSITION (`consumeLots` takes `lots[0]`/`shift`). A SELL re-adds its carried principal to that pool. The first cut stamped the re-add with the SALE date and APPENDED it at the tail (`pushPoolLot` with `event.date`) — so a funding lot acquired BETWEEN the buy and the sale sat AHEAD of the (genuinely-older) re-added principal, and a PARTIAL conversion consumed that NEWER funding first → mis-rated the conversion and shifted an FX gain into the WRONG TAX YEAR. Numerical proof (reproduced by the maintainer): fund $1000@0.80 (Jan) → buy → fund $1000@1.10 (Mar) → sell USD-flat (re-adds @0.80) → convert $1000 in year N, $1000 in N+1 gave **€100 / €500** when correct origin-FIFO is **€400 / €200** — same €600 lifetime, but €300 in the wrong year. **Fix**: each parked slice now carries its consumed pool lot's ORIGINAL `acquireDate` (`null` for an uncovered slice), and the SELL re-adds the principal stamped with THAT date (uncovered → sale date); `pushPoolLot` SPLICES the lot into date-sorted pool position (not the tail), so the pool stays FIFO-ordered by genuine age and `consumeLots` is untouched. Only the carried PRINCIPAL keeps its original date — the trading PROFIT and uncovered/unmatched re-adds correctly stay at the sale date (DGT V0282-22: returned principal keeps its acquisition; profit is newly-acquired). Lifetime total is unchanged; only the per-year split (and the trace's `acquireDate`/`lotId`) moves. Pinned by `tests/integration/fx-carry-basis-e2e.test.ts` ("re-added principal keeps its original acquisition date (FIFO order across years)"), which fails €100/€500 on the pre-fix engine. The dominant funding-absent/uncovered case is unaffected (no tracked origin → sale-date re-add, as before).
- **Doctrine — FX captured across the full holding period via DEFERRAL, not realize-at-buy**: carry-basis is an engine design choice backed by V0282-22 (returned principal keeps its acquisition rate, profit dollars take the sale-date rate), V2422-20 (worked example: no gain on the shares, none on converting the dollars) and Art. 14.2.e (FX imputed "en el momento del cobro o del pago"). Do NOT cite V2324-10 for it: that consulta is about investment funds, not a currency rule (see the citation bullet above). The buy CONSUMES (parks) but does NOT realize, so it does NOT re-arm the missing-prior-year-lots phantom GAIN bug that PR #143 / PR #171 removed (a buy emits no disposal, and an uncovered buy is a safe no-op against an empty pool). A "realize-at-buy" variant (spending dollars on a stock realizes their FX) is explicitly NOT what this implements: newer doctrine (V0282-22 / V0152-26) defers to the conversion, and the variant needs buy-side disposal emission that would re-introduce the phantom; it remains a documented FUTURE follow-up only.
- **Legal-citation (corrected, retained)**: divisa is **Art. 33.1** (transmisión − adquisición), timing **Art. 14.2.e** ("se imputará en el momento del cobro o del pago"), FIFO-for-currency is an inference, not a consulta (no DGT answer applies FIFO to fiat currency; see the parking/ordering bullet); NOT Art. 37.1.l (which governs "incorporaciones que no derivan de transmisión"). The stale "Art. 37.1.l" comment in `report.ts`'s FX block was corrected alongside this work (see the #225 citation correction above).
- **Scope/filter (unchanged)**: only `assetCategory` STK/FUND/BOND, `currency ≠ EUR`, ecb-resolvable; crypto permutas (proceeds in a coin, not fiat — crypto valuation path), options/FOP/FSFOP, and the CASH conversions already handled by `extractFxEvents` are excluded; SHORT legs are skipped (inflow at open, outflow at close — the long-side carry model can't represent them). Gated by monodivisa (`skipFx`), like the rest of the FX engine.
- **The parking/ordering is a REASONED GAP-FILL, not a statutory mandate (issue #230 follow-up, contributor elmasvital)**: the law does NOT prescribe how to FIFO-order a currency when some of it is locked inside an open securities position — it is genuinely SILENT. Art. 37.2 LIRPF's "se considerará… los adquiridos en primer lugar" FIFO is scoped *expressly* "a efectos de las letras a), b) y c)" of 37.1 — i.e. **valores** — and DGT **V1613-25** holds verbatim that *"las divisas no son valores ni participaciones"*, so 37.2 does NOT literally reach currency; FIFO-on-divisa is itself an inference (the base for the divisa GAIN is Art. 33.1 + 35 + timing 14.2.e). So a contributor's "pure global FIFO on the currency (consume the literally-oldest dollars, even those spent on a still-held stock)" is a *defensible reading of a silent gap* — but it is NOT more legally faithful: the only on-point consulta, **V0282-22**, values each dollar tranche by ORIGIN and defers the divisa gain to the actual EUR conversion, which is closer to carry-basis than to pure-FIFO. And mechanically, pure-FIFO ("a stock buy does not remove the FCY it spent from the queue") is byte-identical to the v0.49.0 **full-proceeds model already killed** — it re-opens the €450-vs-€320 drift and un-anchors the wrong-year fix (#240). Verdict: keep carry-basis (most-defensible reading + no regression); the contributor's pure-FIFO is offered only as the discrepancy-CHECK below, never as the engine.
- **FX conservation self-check (`checkConservation`, issue #230 — the contributor's "pool para comprobación de descuadres… que no se silencien operaciones sin respaldo económico")**: an ALWAYS-ON, zero-tax-impact diagnostic run at the end of `processEvents`. Per-currency accumulators (`accAcquired`/`accDisposed`/`accParked`/`accUnparked`/`accDiscarded`/`accProfit`/`accPhantom`, incremented next to each `record()` site) assert the quantity identity `(acquired + profit + phantom) − disposed − discarded == poolBalance + Σ parkedBalance`, within `CONSERVATION_EPS = 0.01` FCY units. It is the regression tripwire for the "pool diverged from the real spendable balance" bug class (the €450/€320 drift). **The `phantom` term is load-bearing**: three documented-legitimate paths put untracked FCY into the books with no real acquire behind them — (1) missing-lot floored disposals (`consumeLots` "sin lotes"/"insuficientes", which floor gain to 0 and never decrement the pool), (2) uncovered park (`parkPrincipal` shortfall, `rate=null`), (3) unmatched-sell re-add (`unparkAndReadd` top-up at the sale rate) — so each increments `accPhantom` by exactly its quantity, making the identity hold EXACTLY (silent) on every legitimate scenario and fire ONLY on a genuine internal descuadre. Emits `fx.conservation_mismatch` (severity `warning`, developer-facing). Runs on ALL-YEAR engine state (before report.ts year-filters), so the identity is scoped to the full `processEvents` run, never the year-filtered casillas. Pinned by `tests/engine/fx-conservation.test.ts` (19 tests incl. a BreakableEngine that proves it fires on a real desync and is silent on sub-EPS dust).

### Real applied FX rate for actual conversions (issue #253 — carves out the "never fxRateToBase / ECB default" rule)
- **What**: a CASH EUR↔FCY conversion may now carry `Trade.realEurAmount` — the REAL, spread-laden EUR principal the broker actually moved on THAT conversion, the separately-itemized `commission`/fee EXCLUDED. When present (finite and positive), the FX engine values that conversion at the effective real rate `realEurAmount / |quantity|` instead of the ECB mid-rate, so the broker's hidden FX spread is captured. The commission is STILL applied on top (Art. 35), so `realEurAmount + commission` = the full real cost of the conversion — the fee is never folded into `realEurAmount` (no double-count). This is a real cash amount FROM the statement — it is **NOT** IBKR's `fxRateToBase`, which remains banned (the "always ECB, never fxRateToBase" rule under *Financial Precision* still holds for every implicit/derived rate). Absent → the engine falls back to ECB.
- **Why**: the broker's FX spread is a deductible cost — **Art. 35.1.a** ("importe real de la enajenación") read with **35.1.b** ("gastos … inherentes"). ECB-mid silently DROPS that spread, overstating the divisa gain (or understating a loss) on a real conversion the taxpayer actually paid the spread on. Reserved for ACTUAL EUR↔FCY conversions where a real euro amount exists in the statement; **ECB stays the valuation** for FCY that arrives with NO euro price (stock proceeds, dividends, interest) and as the fallback whenever no `realEurAmount` is supplied. The maintainer already endorsed this carve-out (issue #242 → #253).
- **V0282-22 nuance**: ECB is the *official* valuation rate, but the "importe real" is, by construction, "ECB minus the disclosed spread" — so this is the SAME figure expressed via the verifiable cash amount on the statement, not a competing rate. It does NOT overturn the ECB-default doctrine; it just prefers the broker's own euro cash figure when the statement discloses it.
- **HOW / the load-bearing INVARIANT (symmetry)**: ONE shared private helper `FxFifoEngine.effectiveRate(event)` (in `fx-fifo.ts`) returns `realEurAmount/|quantity|` when present else `event.ecbRate`, and is called by BOTH `addLot` (acquire) AND `consumeLots` (dispose). So the acquire and dispose legs of a tracked round-trip are ALWAYS valued on the SAME basis — never a half-real/half-ECB mix, which is exactly the asymmetry that would fabricate a phantom gain. When both legs carry `realEurAmount`, the realized FX gain is `realEurReceived − realEurPaid` EXACTLY. Absent field → `effectiveRate` returns `ecbRate` → byte-identical to the prior pure-ECB behavior (the zero-change regression guard).
- **Scope / who populates it**: `extractFxEvents` reads `trade.realEurAmount` (parsing it with `decimal.js`; a non-finite/non-positive/garbage value is dropped → ECB fallback) and attaches it to BOTH the acquire and dispose events it emits. **Lightyear** populates the field today: its conversion rows come in a same-timestamp PAIR (one leg per currency), and `parsers/lightyear.ts` harvests the EUR leg's `|Net Amt.|` (real principal, fee excluded) and stamps it on the non-EUR CASH trade, with the larger `Fee` of the two legs as its commission. The timestamp (to the second) is the only key, so a pair is known only when the second holds exactly two conversion rows, one in EUR and one in another currency (#467: two conversions in one second, or an unreadable EUR leg next to another conversion, gave a leg another conversion's EUR principal, or both legs the larger fee). Any other second (FCY↔FCY, two conversions at once, a leg with no CCY) leaves it unset → ECB, and each leg keeps the fee its own row writes (a fee on an unpaired EUR leg is not booked: a dropped cost, so never an underpayment). Every OTHER broker falls back to ECB until its parser sets the field. Skipped under monodivisa (`skipFx` — the whole FX engine is off), like the rest of the FX engine.
- **Pinned by**: `tests/engine/fx-fifo.test.ts` ("real applied EUR amount (FX spread capture — issue #253)") at the raw-`processEvents` level; `tests/parsers/lightyear-fx-realrate.test.ts` (the parser stamps the field, and `realEurAmount + |fee| == |EUR Gross|`); and `tests/integration/fx-real-rate-e2e.test.ts` end-to-end through `generateTaxReport` and `lightyearParser.parse` → `generateTaxReport` (spread capture = smaller gain by exactly the spread, symmetric reconciliation = realReceived − realPaid, no-field byte-identical, no fee double-count).

### FX-FIFO movement trace (opt-in audit ledger — issue #230)
- **What**: an opt-in `ReportOptions.fxTrace` flag on `generateTaxReport`; when true, `TaxSummary.fxTrace` is populated with an `FxTraceEvent[]` — the full all-year FX-FIFO movement ledger (kinds `acquire`/`dispose`/`park`/`unpark`/`discard`/`profit`, each carrying the running pool and parked FCY balances after the event). Produced by the engine itself: `FxFifoEngine.enableTrace()` records every movement, `getTrace()` returns it. Serialize the array with `serializeFxTrace(trace, "jsonl" | "csv")` (type `FxTraceFormat`) in `src/generators/fx-trace.ts`.
- **Why**: lets a developer/advisor audit exactly how a 1633/1637 figure was built and reconcile it by hand, and makes the carry-basis engine mechanically testable via golden-ledger tests. Born from issue #230 — the reporter was keeping a hand `console.log` ledger to verify the FX math; this turns that into a first-class, lossless artifact.
- **Reconciling to the casillas (load-bearing caveat)**: the trace is the FULL all-year ledger but the casillas are YEAR-FILTERED (`report.ts` keeps disposals whose `disposeDate` ∈ declaration year). So the golden-ledger identity is `Σ dispose.gainLossEur WHERE date∈year === fxGains.netGainLoss` — summing ALL `dispose` rows across years over/under-states the box on any account that converts a tracked currency in more than one year. Pinned by both a single-year and a MULTI-year reconciliation test in `tests/integration/fx-trace-e2e.test.ts`.
- **Where it's exposed**: CLI `--fx-trace [file]` / `--fx-trace-format jsonl|csv`; web offers a download gated behind `#debug` (or `localStorage.declarenta_debug`). **NEVER in the standard UI** — the FX-FIFO is not shown to normal users (the reporter's explicit ask). **Zero-cost when off**: every engine `record()` returns immediately unless `enableTrace()` was called, and the whole thing is skipped under monodivisa (`skipFx`).
- **Per mode**: under «Tradicional con divisa» a loss sale's unreturned principal is a `dispose` row with `trigger` `stock_sale` (lost dollars), `discard` keeps only slices with nothing to book (untracked or zero gain), and `unpark` notes print the shifted cost in two parts. docs/traza-fx.md has the user-facing version.
- **The `discard` kind is the audit-visible proof of the loss-sell principle (default method)**: dollars spent inside a losing position that never converted to EUR appear in the ledger as `discard` (no FX realized), never as `dispose` — the mechanical evidence that an un-converted same-currency loss-sell books nothing into 1633/1637 (see the loss-sell bullet above, Art. 14.2.e).

## Project Philosophy

### Rigorous by default, with an opt-out checkbox when warranted (product posture)
- **Default = maximum fiscal rigor.** When Spanish law/DGT doctrine supports computing something (e.g. the divisa/FX element under Art. 33.1), DeclaRenta computes it by default — even when it is legally soft (inferred from general norms, no binding consulta) and even when no competitor does it. Being the most correct tool is the point.
- **BUT** when a computation is (a) not strictly needed for a correct return, (b) rests on genuinely-unsettled doctrine, or (c) is something other tools commonly omit — provide a **profile checkbox** to turn it off, exactly like the **method choice** does for the FX engine (the default «Criterio DGT (multidivisa)», or «Tradicional con divisa» / «Tradicional sin divisa (monodivisa)» via `reportOptionsForMethod`). Rigorous on, but one click to match the simpler/market-standard treatment and reconcile with other tools.
- Pattern to follow for any future "should we compute this aggressive/contested thing?" question: ship it ON by default, expose an OFF checkbox in the fiscal profile (persisted in localStorage, threaded as a `ReportOptions` flag), and add a Competitor-Reconciliation-style note explaining when to use it. Never silently drop rigor; never force a contested computation with no escape hatch.

### Correctness with User Comfort
- DeclaRenta must be 100% fiscally correct by default
- BUT users should not be alarmed by non-critical warnings or confusing technical output
- "UNKNOWN" lot IDs and multi-line FX warnings for zero-gain events are inelegant — users don't need to worry about these
- **Planned: Three-tier message system** (info/warn/error) to replace flat warnings:
  - **Error**: Blocks report validity — missing data that affects tax amounts
  - **Warning**: User should review but report is still usable — e.g. wash-sale applied, large FX gains
  - **Info**: Informational only, no action needed — e.g. prior-year lots assumed, auto-convert detected
- Current "sin lotes previos suficientes" with gain=0 should be INFO (not warning) — it's handled correctly and needs no user action
- Goal: users who upload their file and see green results should feel confident, not anxious

### Actionable Explanations (Every Tier)
- Every message (error, warning, info) MUST include a brief, localized explanation of **what likely caused it** and **what the user can try**
- Common root causes to suggest: missing columns in the export, incomplete date range (doesn't cover prior years' acquisitions), wrong report type selected from broker
- Example: "Venta sin lotes — ¿incluye tu exportación los años anteriores? Descarga de tu broker un periodo que cubra desde la primera compra de este valor."
- Messages that fire for every broker must not assume IBKR (no "Flex Query" advice there); keep IBKR wording for IBKR-only messages
- These hints are rendered in the user's active locale (use `t()` keys, never hardcoded Spanish)
- The tone is helpful ("try this"), never blaming ("you forgot to...")

### Competitor Reconciliation Hint
- When the final results page is shown, include a subtle note (not a warning) explaining:
  - If other tools (Autodeclaro, Taxdown, etc.) show a different amount, it may be because they value foreign-currency shares at each operation's own-date rate instead of separating the currency result (Art. 33.1, timing Art. 14.2.e LIRPF)
  - Point the user to the method choice on the «Revisar y elegir método» step (CLI `--fx-method`) to compare: «Tradicional con divisa» values shares at the buy-date and sale-date rates and also computes the currency; «Tradicional sin divisa (monodivisa)» values shares the same way but computes no currency result at all, not even on USD→EUR conversions. Never claim currency parity with any tool
  - Wording: the `report.competitor_reconciliation` message and its `.hint` key in the locales
- This hint should appear near the capital gains total, rendered as a collapsible "info" note (not a warning)
- It validates the user's concern ("your numbers are correct, here's why they differ") rather than creating doubt
